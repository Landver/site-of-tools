# RBL / DNSBL & domain reputation lookups

Whole category built on one trick: **DNS as a key-value database**. You don't call an API, you build a hostname out of the thing you're asking about & resolve it. `A` record inside `127.0.0.0/8` = listed, `NXDOMAIN` = not listed, `TXT` = human-readable reason w/ delisting URL. Zero auth, zero HTTP, ~50 ms, & the answer is already cached by whatever resolver you used. For a DNS-lookup tool this is the highest value-per-line-of-Go feature available: `net.Resolver.LookupHost` + a table of zones & you have a 20-list reputation card. Catch is licensing, not engineering: the good lists actively **refuse queries arriving via public resolvers**, & each one refuses differently, including at the RCODE level.

- **URL:** [mxtoolbox.com/blacklists.aspx](https://mxtoolbox.com/blacklists.aspx) · [multirbl.valli.org](https://multirbl.valli.org/) · [spamhaus.org](https://www.spamhaus.org/) · [surbl.org](https://www.surbl.org/) · [uribl.com](https://uribl.com/) · [talosintelligence.com/reputation_center](https://talosintelligence.com/reputation_center/) · **Category:** IP & domain reputation blocklists (DNSBL/RBL/URIBL/DNSWL) + web frontends over them · **Registration:** none for DNS queries to most zones; Barracuda requires free NS registration; Spamhaus DQS / Google Safe Browsing / MXToolbox API require a key · **Pricing:** free for low-volume non-commercial; commercial use = DQS/datafeed/rsync · **API:** DNS itself is the API; HTTP APIs are the exception (MXToolbox REST w/ a metered free key, Talos has none public, Google Safe Browsing/Web Risk are REST)
- **Firsthand check (first pass 2026-09-15, re-verified & extended 2026-09-16, egress `89.222.123.x`, residential, non-datacenter rDNS):** ~90 `dig` queries across 4 resolver paths (system/Google `8.8.8.8`, Cloudflare `1.1.1.1`, Quad9 `9.9.9.9`, direct-to-authoritative) against 25 zones; curled MXToolbox, multirbl, Talos, Safe Browsing, Web Risk & both DoH JSON endpoints; fetched the Spamhaus/SURBL/URIBL/dnswl/MXToolbox-API vendor docs. Reproduced the public-resolver ACL matrix, DBL wildcarding, retirement & wrong-zone sentinels, RCODE-level refusals & TTLs below. **Could not** read Talos at all (403 to `curl` w/ browser UA & to WebFetch, on both the apex & `support.` host) or get a *successful* multirbl JSON row (see Verified section).

## The DNS-as-a-database pattern

| Input | Encoding | Example |
| --- | --- | --- |
| IPv4 | octets **reversed**, dotted, + zone | `1.2.3.4` -> `4.3.2.1.zen.spamhaus.org` |
| IPv6 | nibble format (`ip6.arpa` style), all 32 nibbles reversed | `2001:db8:7ca6:22::45` -> `5.4.0…0.2.2.0.0.6.a.c.7.8.b.d.0.1.0.0.2.<key>.sbl.dq.spamhaus.net` |
| Domain | prepended **unreversed**, zone is wildcarded | `example.com.dbl.spamhaus.org` |
| Hash (Spamhaus HBL) | `base32(sha256)` (RFC 4648) + `._<context>` | `KADTR…GSBA._file.<key>.hbl.dq.spamhaus.net` |
| Multi-list bitmask | last octet = OR of member-list bits | URIBL `127.0.0.14` = black(2)\|grey(4)\|red(8) |

Note the DQS key is a label *between* the encoded input & the zone, not a suffix. Verified against Spamhaus's own query-format doc, whose literal examples are the ones quoted above.

**Return-code namespaces are per-vendor & must be parsed, not truthed.** Spamhaus alone uses four disjoint ranges: `127.0.0.x` IP zones (SBL 2, CSS 3, XBL 4, DROP 9, PBL 10 ISP-maintained / 11 Spamhaus-maintained, AuthBL 20, BCL 30), `127.0.1.x` DBL (2 low-rep, 4 phish, 5 malware, 6 botnet C&C, 102 abused-legit, 103 abused redirector, 104/105/106 abused-legit phish/malware/C&C), `127.0.2.x` ZRD (2–24 = hour-age buckets), `127.0.3.x` HBL (2 email, 10 malware file, 15 suspicious file, 20 crypto wallet, 30 URL). **`127.255.255.x` is not reputation at all**: `.252` = wrong blocklist address, `.254` = query via public/open resolver, `.255` = excessive volume, `.250/.251` = DQS key disabled / illegally used. A tool that treats any `127.*` as "listed" reports a resolver problem as a spam verdict. Two more traps in the same vein, both observed: **DBL answers an IP-literal query w/ `127.0.1.255`** (in-range, looks like a DBL hit, actually means "wrong input type"), & **`127.0.0.1` means opposite things per vendor**: URIBL/SURBL use it for *refused*, while `dnsbl.dronebl.org` returns `127.0.0.1` + TXT `"Testing class."` as a genuine *listing* (my own `dig`; DroneBL publishes no return-code table). SURBL packs six lists into one bitmask (DM 4, PH 8, MW 16, CT 32, ABUSE 64, CR 128; `127.0.0.80` = MW+ABUSE, the vendor's own worked example). URIBL uses 2/4/8 for black/grey/red, 16 for datafeed-only `gold`, & `127.0.0.255` for rate-limited.

**Observed TTLs (firsthand).** ZEN hit `60`, DBL hit `60`, ZEN negative-cache SOA minimum `10`. URIBL's *refusal* caches for `2100` s, i.e. once you're ACL'd from a resolver you stay ACL'd for 35 min of that resolver's cache. Spamhaus SOA serial is a date stamp (`2609160938` = 2026-09-16 09:38 UTC) -> free freshness indicator for a UI.

| `dnsbl.sorbs.net` | NXDOMAIN (SORBS decommissioned) | n/a | NXDOMAIN | n/a |

Three things this matrix actually proves. First, **the ACL is per-resolver-egress-IP, not a blanket policy**: Spamhaus answered Quad9 fine while blocking Google & Cloudflare on the same second. That can flip any day; don't hardcode "use Quad9". Second, **the refusal is informative**, which is the whole design: URIBL tells you *which* resolver IP got you banned, Spamhaus links a per-IP explanation page (& for Cloudflare names its IPv6 egress, so the ACL is v6-aware). Third, **not every refusal is a 127.x answer**: manitu refuses at the RCODE level, which a naive "`NXDOMAIN` = clean, anything else = listed" branch gets exactly backwards. Spamhaus's own policy is explicit that free use requires queries "are not being made from a public resolver or an IP with generic rDNS", which also rules out AWS/GCP/Azure/Hetzner egress. A hosted tool therefore wants **its own recursive resolver on a non-generic-rDNS IP**, or a DQS key, or it queries only the lists that tolerate public resolvers.

## Features — complete inventory

### MXToolbox blacklist check (the category's default answer)
Single input box (`Server IP or Domain`), fans out to **"over 100"** DNSBLs (firsthand: that string is in `blacklists.aspx`'s own server-rendered HTML, `lblNumberofBlackLists`), renders one row per list. Table-stakes: per-list listed/not-listed, delisting link. Distinctive: it's the **SuperTool** frame, so the same box runs 30-odd other lookups via a `command:argument` prefix syntax, each producing a permalink result page. The API reference gives the authoritative command list: **DNS** `a`, `aaaa`, `asn`, `bimi`, `dkim`, `dmarc`, `dns`, `mta-sts`, `mx`, `ptr`, `soa`, `spf`, `tlsrpt`, `txt`; **network** `blacklist`, `http`, `https`, `ping`, `smtp`, `tcp`, `trace`. (`whois:`/`arin:` exist in the web SuperTool but are *not* in the API list.) Beyond the matrix it also ships a DMARC record generator, DMARC report analyzer, header analyzer, bulk lookup, MxReputation Score, Domain Health, outbound-email-sources report, & novelty `llms.txt` / AI-robots checkers, plus **blacklist monitoring** & the Delivery Center product. **Firsthand on the API:** unauthenticated `GET api.mxtoolbox.com/api/v1/lookup/blacklist/1.1.1.1` -> **HTTP 401** `"You are not authorized to access the API…"`. Auth is `Authorization: <uuid>` w/ **no `Bearer` prefix**, & there *is* a free key tier: **64 DNS requests/day, 0 network requests**, quotas resetting 00:00 UTC, `429` when exceeded. Since `blacklist` is a *network* request, **the blacklist API is paid-only even w/ a free key** — the free tier buys you plain DNS lookups. Still unverified (2026-09-16): pricing (Delivery Center from **$129/mo**, Plus **$399/mo**) & the free-monitor split (1 domain, weekly, **top 30** lists; paid moves to 100+ & multiple checks/day). `mxtoolbox.com/pricing` 404s, `/Public/Pricing.aspx` 302s to an error page, & the product page shows no numbers, so those come from review sites only.

### multirbl.valli.org (the one worth copying architecturally)
Free, no account, no API key, ad-supported. Test modes: **FCrDNS & DNSBL lookups** (combined), FCrDNS alone, DNSBL lookups alone, Whois lookup, and **"Test by sending an email"** (you mail their address, they report what your sending IP looks like). Firsthand on `/lookup/1.1.1.1.html` the page declares its own workload in a JS global `g_data`: **202 blacklist + 13 combined-list + 26 whitelist + 17 informational-list tests = 258 rows**, each w/ its own counter set. The counters are per-table, not global, which is why the header reads "n of 202" on the big table rather than "n of 258".

Two mechanics worth the paragraph. **(1) Per-list input routing.** The server renders the table *with the query hostname already computed per row*: for `1.1.1.1` exactly **199 rows carry `l_qhost = 1.1.1.1`** while **59 rows carry `l_qhost = one.one.one.one`**, the rDNS name, because those are URI lists (`black.uribl.com`, `multi.surbl.org`, `uribl.swinog.ch`, `nuribl.mailcleaner.net`…) that index names, not addresses. One user input, resolved forward & backward, then each list gets whichever form it actually indexes. **(2) Render-then-fill.** The HTML ships all 258 rows synchronously with `<td class="result">Status</td>` placeholders; `lookup.js` then fires one `$.post('/json-lookup.php', 'ash=<session>&rid=<rowid>&lid=<numeric list id>&q=<qhost>')` per row. `lookup_callback` reads `lud.data.failed` / `lud.data.listed` for the three real states (`Failed` / `Listed` / `Not listed`) & takes the *color* from a **server-supplied `lud.result_color`** ∈ `black|brown|yellow|white|neutral|default`. So the six-color vocabulary is a per-list severity the server assigns, not a client-side decode of the return code. On a hit it injects sub-rows for `Query:`, `A Record:`, **`TTL:`**, per-code `description` & `comments_if_listed`. No spinner blocking the page, no batching, no websocket. It also ships `/list/` & `/detail/<zone>.html`, a **per-zone dossier** (operator, homepage, listing policy, delisting policy) for every zone it queries.

### Spamhaus
Zones (public mirrors): `sbl`, `css`, `xbl`, `pbl`, `sbl-xbl`, **`zen`** (SBL+CSS+XBL+PBL in one query), **`dbl`** (domains), `authbl`. DQS-only zones: **`zrd`** (Zero Reputation Domains, `127.0.2.2–24` = hour-age buckets), **`hbl`** (hashes of files/crypto wallets/emails/URLs), `dwl`/`_vouch` (DKIM whitelist). Firsthand: `zrd.spamhaus.org` on the public side answers **`CNAME blocklist.address.is.wrong.spamhaus.org` -> `A 127.255.255.252` + TXT "Spamhaus blocklist address is wrong. Please read documentation carefully."**, a deliberate wrong-zone sentinel, not NXDOMAIN. Retired `swl.spamhaus.org` answers `127.0.2.2` + TXT **"This list is no longer in operation, please deconfigure it."** DBL is **wildcarded**: `www.dbltest.com` & `deep.sub.dbltest.com` both return `127.0.1.2`; feed it an IP literal & it returns `127.0.1.255` + TXT `"No IP queries for DBL, see …"` rather than a bogus miss. **DQS free tier (vendor pages, read 2026-09-16):** free account; the Fair Use Policy states verbatim that volume "must not consistently exceed **100,000 queries per day**" & that the service is for non-commercial small orgs & individuals. ### Google Safe Browsing / Web Risk
Not DNS at all, but the reputation source most people actually mean by "is this domain dangerous". **v4** (legacy, superseded; the reference page does **not** publish a turndown date): `threatMatches:find`, `threatListUpdates:fetch`. **v5**: `GET /v5/hashes:search` (send 4-byte hash **prefixes**, privacy-preserving), `GET /v5/hashLists/list`, `GET /v5/hashLists:batchGet`, `GET /v5/hashList/get`; `GET /v5alpha1/urls:search` exists in alpha. ## How it works

Every one of these is **server-side from the browser's perspective but client-side from the service's**: the "lookup" is a recursive DNS query your resolver makes, & the vendor's authoritative server sees only your *resolver's* IP, never yours. That's precisely why the ACLs exist & why they misfire on shared resolvers. Frontends (MXToolbox, multirbl) run the queries from their own infrastructure w/ their own resolvers, which is how they stay unbanned; the result page you see is their resolver's answer, not yours. Caching is entirely conventional DNS caching: short positive TTLs (60 s) so delisting propagates fast, short negative TTL (10 s SOA minimum) so a fresh listing lands fast.

Fan-out is embarrassingly parallel & cheap: **8 concurrent `dig` calls against 8 zones completed in 0.54 s wall clock**, firsthand (re-measured 2026-09-16; 0.58 s on the first pass). 40 lists in a Go `errgroup` w/ a 2 s per-query timeout is a sub-second card.

## Output & UX

MXToolbox: one row per list, red/green status, delisting link, permalink result URL, shareable. multirbl: the render-then-fill table described above, w/ a **live counter row** per category (`n of 202 tests done`, then a breakdown across the six verdict colors). The counter is the actual UX win, because 258 rows is unreadable but "3 blacklisted of 202" is not. On a hit it expands the row inline w/ the exact query hostname, the raw `A` record, the **TTL**, the decoded code description, & the list's own comment. Spamhaus & Talos give a single-object dossier page instead of a matrix, w/ a delisting/dispute path as the primary CTA. Empty state across all of them is the same & is the right one: "not listed" stated positively per list, never as an error.

## Monetization, limits & abuse controls

Uniform shape: **free for low-volume non-commercial DNS queries, paid the moment you're commercial, high-volume, or want the good zones.** Enforcement is layered: (1) resolver ACLs (Spamhaus, SURBL, URIBL, DNSWL) & RCODE refusals (manitu), (2) per-resolver volume caps w/ a dedicated return code (DNSWL 100 k/24 h -> `127.0.0.255`; Spamhaus -> `127.255.255.255`), (3) registration of querying NS IPs (Barracuda), (4) key-in-the-hostname metering (Spamhaus DQS, 100 k/day free), (5) HTTP-layer blocking & metering of the web UIs & APIs (Spamhaus 403, Talos Cloudflare 403, MXToolbox 401 then 64 DNS-only requests/day on a free key, Google 403 `PERMISSION_DENIED`). Note the asymmetry a hobby tool should respect: **DNS queries are cheap & tolerated; scraping the web UIs is explicitly not.**

## Cross-reference: what this repo has, & what a domain-side version adds

`tools/iptools/blocklist.go` already has the right shape: a shared `ip_blocklist` Mongo corpus, TTL index via `platform.EnsureTTLIndex`, `RangeStart/RangeEnd` uint32 containment for netblocks, `syncFeed` + `runDailySync` scaffolding, & `BlockLookup{Sources, MaxCount}` as the reader's view (all symbol names confirmed against the file). `spamhaus.go` ingests **DROP** (~1,669 IPv4 CIDRs, JSON Lines, license satisfied by stamping copyright into `Meta`); `ipsum.go` ingests ~118 k IPs w/ a 0–10 corroboration count.

What that architecture **cannot** answer today is any question about a *name*. DROP & ipsum are IP-only & bulk-downloadable; DBL, SURBL, URIBL, ZRD are domain-only & **query-only**: there is no downloadable DBL, so a domain-side feature is structurally a live DNS query, not a corpus sync. Concretely, a DNS-lookup tool gains: is this domain listed as spam/phish/malware/botnet-C&C (DBL `127.0.1.2/4/5/6`), is it a disposable-mail or click-tracker domain (SURBL DM/CT), is it newly registered (ZRD/SURBL fresh), & is its *mail* infrastructure clean (resolve MX -> A, then run each MX IP through the existing IP-side corpus + ZEN). That last one is the real fusion point: the domain the user typed, its MX hosts, and `BlockList.Check` on each resolved IP, in one card.

Firsthand proof the two sides corroborate: ipsum's top-count IP `138.226.239.234` (count 10) -> ZEN `127.0.0.4` (XBL, TXT confirms), UCEPROTECT L1 `127.0.0.2`, blocklist.de `127.0.0.4`, but **not** listed by SpamCop or Barracuda. Five sources, three hits: exactly the "n of m agree" signal `MaxCount` already models.

## Ideas worth stealing

- **Render-then-fill, htmx-native.** multirbl's mechanic maps 1:1 onto this stack w/o a line of custom JS: server renders the full list table w/ one `<tr hx-get="/dnsbl/check?zone=…&q=…" hx-trigger="load" hx-swap="outerHTML">` per zone. 40 rows = 40 parallel requests the browser manages, each handler doing one `LookupHost` + returning one `<tr>`. Domain logic stays a pure `func Check(ctx, zone, query) Result`, handler negotiates HTML-fragment vs JSON per rule #2.
- **Per-list input routing.** Derive *both* forms from one input: for an IP, also resolve rDNS; for a domain, also resolve A/AAAA & MX. Then tag each zone in your table as `kindIP` or `kindDomain` & feed it the right form. Copy multirbl's `l_qhost` idea (199 vs 59 rows on one input): compute the exact query hostname server-side & show it in the expanded row, so the result is reproducible w/ `dig`.
- **Decode codes, never truth `127.*`, & branch on RCODE first.** Ship a `map[string]map[string]string` of zone -> return code -> description, & hard branches for `127.255.255.x` (Spamhaus), `127.0.1.255` (DBL wrong input type), URIBL/SURBL `127.0.0.1` & `127.0.0.255`, DNSWL `127.0.0.255`. Then, *above* that, branch on the RCODE: `REFUSED`/`SERVFAIL` (manitu) is a distinct "refused" state, & `NXDOMAIN` is the only real "clean". And remember `127.0.0.1` is per-vendor: refused on URIBL, a listing on DroneBL. This is the single most common bug in amateur DNSBL tools.
- **Verdict vocabulary wider than listed/not.** multirbl's design is right, but copy it accurately: three *states* (Listed / Not listed / Failed) crossed with a per-list *severity color* you assign in your zone table (black/brown/yellow/white/neutral). Whitelist hits (DNSWL, URIBL white) are *positive* evidence & must not render as red.
- **Retirement & wrong-zone sentinels.** Spamhaus answering `"This list is no longer in operation, please deconfigure it."` on a dead zone, & `127.255.255.252` + `blocklist.address.is.wrong.spamhaus.org` on a typo'd one, are both better than NXDOMAIN. Worth mimicking in any list-of-zones config: mark zones `retired` / `dqs-only` in the table & render why, rather than silently dropping them.
- **Show the TTL & the SOA serial.** multirbl surfaces per-answer TTL; Spamhaus's SOA serial is a timestamp. Both cost nothing & make the result feel like a measurement rather than a scrape. Requires `miekg/dns` (or a raw query) since `net.Resolver` hides TTLs, a real dependency decision to make consciously.
- **Rollup line above the table.** "3 listed · 1 whitelisted · 36 clean · 2 failed, of 42 lists": the only thing that makes a long matrix readable, & it's a live counter as rows fill in.
- **DoH as a resolver escape hatch — verified usable from a browser.** Both `cloudflare-dns.com/dns-query` (`accept: application/dns-json`) and `dns.google/resolve` return `access-control-allow-origin: *` on a GET w/ a cross-origin `Origin` header, firsthand, so client-side DNSBL queries are technically possible. (Cloudflare 415s a `HEAD`, so probe w/ GET.) Two caveats that probably kill it here: Cloudflare is ACL'd out of Spamhaus (`127.255.255.254`) & SERVFAILs on SURBL, & a client-side query answers "is this IP listed *from the visitor's resolver*", which is a different question. Keep it server-side; keep DoH in the back pocket for a "check from a second vantage point" toggle.
- **Zone dossier pages.** multirbl's `/detail/<zone>.html` (operator, policy, delisting path) is cheap static content that makes the tool authoritative rather than a proxy, and it's markdown-in-`docs/`, which this repo already renders.
- **DQS as the documented upgrade.** Because the key is just a DNS label, `zen.spamhaus.org` -> `<key>.zen.dq.spamhaus.net` is a `fmt.Sprintf` behind a config var. Build for the free public zones, leave the seam.

## Gaps & what it does not do

DNSBLs answer **listed / not listed**, not "how bad": there's no score, no confidence, no first-seen date in the DNS answer (ZRD's hour buckets are the lone exception). They're mail-centric: a domain clean on DBL can still be a scam site, which is what Safe Browsing/Talos cover & DNS does not. Delisting is out-of-band & per-vendor. Nothing here is a *history*: you see now, not last week (which is exactly what this repo's Mongo lookup-history pattern could add for free). And the whole category is unusable at volume from cloud egress w/o a key, which is a deployment constraint, not a feature gap.

## Open source / reusable

Go DNSBL helpers exist but are thin & mostly unmaintained wrappers, both **MIT** (verified from their `LICENSE` files): [`polera/gorbl`](https://github.com/polera/gorbl) (MIT, © 2015 James Polera, stdlib-only, `gorbl.Lookup(zone, host)` per zone) & [`mrichman/godnsbl`](https://github.com/mrichman/godnsbl) (MIT, © 2016 Mark Richman) w/ forks (`rbeuque74`, `HENNGE`, `daliand`). godnsbl's JSON result is `{rbl, address, listed, text, error, error_type}`, slightly richer than a bare listed/text pair, but neither decodes return codes & neither knows about the refusal codes or RCODE refusals, which is the part that matters. Both still carry Travis-CI badges, a fair proxy for how long since anyone touched them. Realistically: write ~80 lines against `net.Resolver` (or `miekg/dns` if you want TTLs) & put the value in the **zone table & code decoder**, which is data, not code. Upstream data worth vendoring: multirbl's `/list/` + `/detail/` corpus as a starting zone inventory, Spamhaus's published return-code tables, SURBL's & URIBL's bitmask tables, dnswl's category table.
