# Implementing DNS lookups in Go

Every feature the DNS-tool reports want (arbitrary RR types, TTLs, resolver flags, DNSSEC chain, `+trace`, resolver comparison) is gated on one decision: **which DNS layer we build on**. Go's stdlib `net.Resolver` is the obvious start & the wrong one; it structurally cannot express most of the feature list. This assesses the real candidates w/ pinned versions, maintenance state, measured binary cost, and shows where a `dns` domain package sits under the repo's layering rules. No tool design here, no Go written for the tool.

- **Scope:** Go-side implementation only (libraries, transports, concurrency, caching, deps). Sibling reports cover what competing *services* show. · **Why it matters for our build:** picking `net.Resolver` today silently deletes ~70% of the feature inventory; picking a heavy framework breaks the "one small binary, few deps" rule. Also: **the de-facto library just entered maintenance mode**, which changes the pin decision.
- **Firsthand check (2026-09-15, Go 1.26.5 darwin/arm64, scratch modules):** ran `net.Resolver` against its own limits; ran `github.com/miekg/dns` v1.1.73 for TTLs/flags/EDE/NSID/DNSSEC verify/TCP fallback/DoT/in-process test server; wrote a working `dig +trace` walk (root -> `com` -> Cloudflare, 3 hops); ran `domainr/dnsr`; parsed CAA w/ `x/net/dns/dnsmessage` (raw bytes); attempted `codeberg.org/miekg/dns` v2 (**refused: needs Go ≥1.27**); DoH wire POST/GET & DoH JSON against Cloudflare / Google / Quad9 w/ `curl` + Go; measured binary-size deltas w/ `CGO_ENABLED=0 -ldflags="-s -w"`.
- **Re-verified 2026-09-16 (second pass, same machine).** Most of the above held. Three numbers did not and are corrected below: the truncation observation, the public-resolver rate-limit claim, and the `dnsproxy` dependency count.
- **Fact-check pass 2026-09-16 (adversarial, same machine).** Re-ran the highest-stakes claims against live sources: GitHub/Codeberg APIs, raw READMEs & go.mod files, a fresh `go build` of `miekg/dns` v1.1.73, and live queries against the root servers, Cloudflare, Google & Quad9. Almost everything held exactly (incl. `TypeToString`=88, `TypeToRR`=80, the `org` DS value, the `cloudflare.com` HTTPS rdata, the CD=1 bypass, the four Cloudflare DoH JSON params). Four things did not and are fixed below: a wrong dependency attributed to `dnsproxy`, the binary-size delta (much more code-path-sensitive than a single number implies), the goresolver validation-scope claim (too narrow, and a real crash bug found), and the Codeberg v2 "will it ever tag v1.0" question (the README actually answers this).

## The mechanics

A lookup is a **UDP/53 exchange** of a packed message: header (ID, flags `RD`/`RA`/`AA`/`TC`/`AD`/`CD`, rcode) + question + answer/authority/additional sections of RRs, each w/ name, type, class, **TTL**, rdata. Everything a DNS tool shows lives in those fields, so the library question is really *does it hand me the message or a convenience summary*.

Four mechanics decide library choice:

1. **EDNS(0) (RFC 6891).** An OPT pseudo-RR carrying advertised UDP buffer size + option codes. Without it you cannot set **DO** (request DNSSEC records), cannot receive **EDE** (RFC 8914 extended error), cannot send **NSID** (RFC 5001, which node answered), **ECS** (client subnet), DNS cookies (RFC 7873, `EDNS0COOKIE`=10) or padding (RFC 7830, `EDNS0PADDING`=12). Re-measured against `a.root-servers.net` (198.41.0.4), `. NS`, RD=0: no EDNS -> 13 answers, no TC; `buf=1232 do=false` -> 13 answers, 27 additional; `buf=1232 do=true` -> **14 answers** (13 NS + 1 RRSIG).
2. **Truncation -> TCP.** `TC=1` means retry over TCP, and `miekg`'s `dns.Client` does **not** do it for you. Re-measured: `buf=512 do=true` -> `TC=true`, and **the answer section is still populated (13 RRs)**; the same query w/ `Net:"tcp"` -> `TC=false`, 14 answers. **Detect truncation w/ `msg.Truncated`, never w/ `len(msg.Answer)==0`** (an earlier draft of this report claimed `ans=0` here; that is wrong, and code written to that claim would silently serve a partial RRset). Caller-side retry is ~5 lines & is mandatory for TXT/DNSKEY/large-RRset queries.
3. **Recursive vs iterative.** Asking `1.1.1.1` (RD=1) = **stub**; walking root -> TLD -> authoritative yourself (RD=0, follow NS + glue) = **iterative**, which is what `dig +trace` shows and what exposes delegation, glue, and DS records.
4. **DNSSEC.** DO bit asks for RRSIGs; **AD** is the *upstream resolver's* claim, not proof. Real validation = fetch DNSKEY, `RRSIG.Verify(key, rrset)`, then match the zone KSK against the parent's **DS** digest, repeating to the root anchor. Firsthand on `cloudflare.com`: `sig.Verify(keytag 34505)` -> `nil`, `ValidityPeriod(now)` -> `true`, `KSK.ToDS(2)` digest == parent DS keytag 2371. The library gives the primitives; **the chain walk is caller code**.

## What the popular tools actually do about it

Essentially all of them sit on **`github.com/miekg/dns`**: CoreDNS, Consul, Mesos-DNS, DNSControl, dnscrypt-proxy, AdGuard & a long README user list. Nothing else in Go has the RR coverage.

**The maintenance fact that matters.** `github.com/miekg/dns` v1.1.73 (tagged 2026-08-19, BSD-3-Clause per `LICENSE`, 8,771 stars, 88 `.go` files incl. tests / ~34.4k lines, re-counted 2026-09-16) README now opens with: DNS v2 lives at `codeberg.org/miekg/dns` and "should be 2x faster across the board", plus *"The version here will only see specific fixes and nothing else. At some point this repo will be archived."* (fetched raw, re-read 2026-09-16). So v1 = **maintenance-only but still shipping**: GitHub API shows **0 open issues** and commits after the tag (`pushed_at` 2026-09-01), repo not archived (all re-confirmed via `api.github.com/repos/miekg/dns`, 2026-09-16).

v2 is not a drop-in and is not ready for us. ## Options for us, w/ trade-offs

Binary sizes measured on one machine (darwin/arm64), `CGO_ENABLED=0 -trimpath -ldflags="-s -w"`, same trivial `net/http` program as baseline (3,565,666 B; this pass rebuilt the same baseline on a slightly different Go 1.26.5 toolchain and got 3,378,594 B — a ~200 KiB toolchain/version wobble, noted so the deltas below aren't read as more precise than they are). Current `site-of-tools` binary for scale: **15,991,762 B (15.25 MiB)** (not independently rebuilt this pass — an unrelated untracked file at the repo root currently breaks `go build .`, so this number is carried over from the prior pass, unverified here). Linux/amd64 deltas will differ somewhat.

**Correction on the miekg/dns delta specifically.** Re-measured this pass by linking increasingly complete usage on top of the `net/http` baseline: a program that only constructs a `dns.Msg` added **~210 KiB**; adding `Pack`/`Unpack`, `dns.Client{Net:"tcp-tls"}`, `dns.NewRR` across 13 RR types, `RRSIG.Verify` and `NewZoneParser` added **~0.92 MiB**; additionally referencing `dns.Server.ListenAndServe` (UDP server code, which the domain-package sketch below only needs in tests, not in the shipped binary) pushed it to **~2.29 MiB**. So "+1.68 MiB" is a plausible point somewhere on that curve, not a fixed cost — the real number depends entirely on which of the library's code paths the finished handler actually calls, and won't be known precisely until that code exists. Treat the table's MiB figures as order-of-magnitude, not exact.

**Recommendation w/ ~85% confidence: pin `github.com/miekg/dns v1.1.73`**, add `golang.org/x/sync/errgroup` + `singleflight` (module already in our graph as indirect), keep `net/http` DoH as an optional secondary transport. Rationale: it is the only option that covers the whole feature inventory, the ~1–2 MiB it costs (see caveat above) is acceptable at any point in that range, and maintenance-only ≠ abandoned (tagged 4 weeks ago, 0 open issues, commits since). Revisit v2 when it tags ≥v1.0 *and* our Go pin reaches 1.27 — per the v2 README's own stated target that's roughly 2028, so this is a multi-year wait, not a quarter. If DoQ ever becomes a requirement, miekg cannot do it and that decision reopens.

### Feature inventory this unlocks (what the owner can pick from)

Table-stakes, one line each: A/AAAA/CNAME/MX/NS/TXT/SOA/PTR/SRV lookups · choice of resolver · TTL display · rcode + flag display (`AA/TC/RD/RA/AD/CD`) · query timing.

Worth a sentence each because they are the differentiators:

- **Arbitrary + modern RR types.** `CAA`, `DS`, `DNSKEY`, `CDS`/`CDNSKEY` (RFC 7344 delegation maintenance), `TLSA`, `SMIMEA`, `SSHFP`, `SVCB`/`HTTPS`, `NAPTR`, `LOC`, `URI`, `DNAME`, `ZONEMD`, `RESINFO`, and raw numeric qtypes (`TYPE65534` packed & sent fine firsthand). Confirmed live 2026-09-16: `org DS -> 26974 8 2 4FEDE294C53F…`, and `cloudflare.com` TYPE65 rdata decodes to `alpn="h3,h2"` + `ipv4hint=104.16.132.229,104.16.133.229`.
- **`+trace` delegation walk.** ~60 lines: RD=0 from a root IP, read NS in authority + glue in additional, hop. Firsthand for `www.corpberry.com`: root `198.41.0.4` -> `l.gtld-servers.net` (`com.`) -> `lisa.ns.cloudflare.com` -> `AA=true` answer, ~240ms/hop. Shows glue, sibling-NS resolution when glue is absent, and DS at each cut.
- **DNSSEC panel.** DO bit + `AD`, RRSIG expiry (`RRSIG alg=13 keytag=34505 signer=cloudflare.com. expiry=20260916214530`), KSK/ZSK split, `KSK.ToDS()` vs parent DS. Full chain-to-root validation is our code (or `goresolver`).
- **Denial-of-existence detail.** NXDOMAIN/NODATA responses carry `NSEC`/`NSEC3` + their RRSIGs in the authority section; miekg types both (`TypeNSEC3`=50, `TypeNSEC3PARAM`=51) and `NSEC3.Match`/`Cover` exist. Shows *why* a name is absent, which the consumer tools skip.
- **Extended DNS Errors (RFC 8914).** The single best "why did this fail" feature, and almost no consumer tool surfaces it. Re-verified firsthand 2026-09-16 on `dnssec-failed.org`: Cloudflare `SERVFAIL, EDE code=9 DNSKEY Missing "no SEP matching the DS found for dnssec-failed.org."`, Google `code=9 "No DNSKEY matches DS RRs of dnssec-failed.org"`, Quad9 `code=6 DNSSEC Bogus` (empty extra text). Same query w/ `CD=1` to Cloudflare -> `NOERROR`, 2 answers, `AD=false`, EDE still attached, a free "validating vs not" demo.
- **NSID.** Which anycast node answered; re-verified 2026-09-16: `1.1.1.1 -> "txl01"`. Quad9's value drifted between passes (`res710.qbre1` first pass, `res711.qbre1` this pass) — expected for an anycast identifier tied to routing/load, not a fixed fact, so don't hardcode a specific node string anywhere. Cheap, and nothing else in our tool belt shows PoP identity.
- **Multi-resolver comparison / propagation view.** Same question fanned out to N resolvers or to the zone's own NS set, diffing answers, TTLs and AD. Pure concurrency, no new deps.
- **ECS (client subnet).** Ask "what would a user in AS X see", pairs directly w/ the existing IP tool.
- **Reverse/PTR + zone-file output.** `dns.ReverseAddr("2606:4700:4700::1111")` -> `1.1.1.1.0.0.…0.7.4.0.0.7.4.6.0.6.2.ip6.arpa.` (verified); RRs `String()` in zone-file format, i.e. a copy-pasteable `dig`-style answer section for free.
- **Available but deliberately out of scope: AXFR/IXFR.** miekg has a zone-transfer client. Running it against third-party zones is hostile; if ever shipped, restrict to our own zones.

### How a `dns` domain package sits under the existing rules

Straight application of ARCHITECTURE §4 + §8, no new patterns:

- `tools/<tool>/lookup.go` — domain. `type Service struct{ resolvers []Resolver; cache *Cache; timeout time.Duration }`, `func (s *Service) Lookup(ctx context.Context, name string, types []uint16) (*Result, error)`. Pure Go, no `echo` import, returns a struct w/ json tags exactly like `iptools.Result`, whose optional `Shodan *ShodanInfo` / `omitempty` sub-section is the precedent for an optional `DNSSEC *DNSSEC` block.
- `trace.go` — the iterative walk, also pure, returning `[]Hop`.
- `handler.go` — `Register(e *echo.Echo, svc Resolver)` + handlers that parse `?name=`/`?type=`/`?resolver=`, call domain, `platform.Respond(c, code, res, "dns/index", "dns/result")`. Free HTML + JSON + htmx fragment, same as `iptools`.
- **Handler depends on a small interface** (`type Resolver interface { Lookup(ctx, …) (*Result, error) }`), mirroring `iptools.Looker`, so `tests/` injects a fake w/ no network.
- **Tests w/o network, for real.** miekg's `dns.Server` binds an ephemeral 127.0.0.1 UDP port in-process; firsthand a handler-registered `test.invalid.` zone answered A/MX in **111–891 µs** and NXDOMAIN for TXT. That satisfies rule #6 without the "skip if BIN absent" escape hatch the IP tool needs.
- **Persistence stays below domain** (rule #5): a lookup-history repository shaped like `tools/iptools/history.go`, nil-safe when `MONGODB_URI` is empty, TTL index via `platform.EnsureTTLIndex`.
- **Cache is in-process, not Mongo.** DNS TTLs are seconds-to-minutes; a `map[key]entry` + `sync.RWMutex` (or `hashicorp/golang-lru/v2`, though that is a new dep for little gain) keyed `name|type|resolver`, expiring at `now + min(TTL over the RRset)`. Negative answers cache for `min(SOA.Minimum, SOA.TTL)` per RFC 2308 §5, not the answer TTL. **Never cache past TTL**, a DNS tool that shows stale data is worse than no tool.
- **Concurrency.** Fan out RR types w/ `errgroup.WithContext` + `SetLimit`; treat per-type failures as partial results, never fail the page. Measured: 12 RR types **serial 3.06 s vs errgroup(limit 8) 477 ms**, same answers, clean under `-race` w/ one shared `*dns.Client`. `singleflight.Group` collapsed **10 concurrent identical lookups into 1** upstream query, the cheapest protection against a hammered public resolver.

## Hard constraints & failure modes

- **Outbound UDP/53 from the Hetzner box is the single project risk & is still unverified.** Cloudflare proxying is irrelevant (it is inbound). If the host or Docker egress blocks :53, every plan above except DoH dies. Neither pass could reach the box, and `docs/DEPLOYMENT.md`, the Dockerfile and compose files say nothing about egress or firewalling, so there is no paper trail to infer from. **Test on the box before writing code** (`dig @1.1.1.1 example.com`, `dig +tcp`, `dig @198.41.0.4 . NS` for the root-walk path). Mitigation is proven from here: DoH over 443 works, `POST application/dns-message` for `example.com A` returned **HTTP 200 / 61-byte body** from Cloudflare, Google *and* Quad9 on 2026-09-16.
- **`net.Resolver`'s limits are structural, not a matter of effort.** MX returns `{Host, Pref}` and nothing else, **no TTL anywhere in the API**. Multi-string TXT records are **concatenated w/o separator** (Go 1.26.5 `net/lookup.go`, `goLookupTXT` at L853, comment at L890: "concatenated without separator to be consistent"), so DKIM split boundaries are unrecoverable. And a gotcha that will waste an hour: with a custom `Dial`, `*net.DNSError.Server` reports the **configured** server, not the dialed one, firsthand a lookup dialed to `127.0.0.1:59` failed with `lookup example.com on 1.1.1.1:53: … 127.0.0.1:59: connection refused`.
- **cgo vs pure-Go resolver is a non-issue for us, by accident.** Our Dockerfile builds `CGO_ENABLED=0` onto `distroless/static`, so the pure-Go resolver is the only one compiled in. On a dev Mac the cgo resolver can be chosen instead (macOS is on Go's list of systems that prefer it), which is one more reason not to build the feature on `net.Resolver` at all. `GODEBUG=netdns=go+1` prints the decision.
- **User-supplied resolver = SSRF-adjacent.** `?resolver=` pointed at `127.0.0.1`, `169.254.169.254`, or a private range turns our server into a probe of our own network, and pointed at an arbitrary public IP turns it into a reflector. Allowlist resolvers (name -> IP) or reject non-public destinations, and rate-limit.
- **Truncation & buffer size.** Advertise 1232 (the DNS Flag Day 2020 number, since codified in RFC 9715 to avoid IP fragmentation), branch on `msg.Truncated` (not on an empty answer section, see mechanic #2), retry over TCP, and cap response handling. Without this, DNSSEC-signed and TXT-heavy queries silently return a partial RRset that *looks* complete.
- **Public-resolver etiquette, w/ the numbers that do exist.** Google publishes one: its troubleshooting page warns about an IP "generating more than 1000 queries per second, which can trigger rate limiting", and its ISP guidance defaults to 1500 QPS per client IP. Quad9's forwarder best-practice doc asks operators expecting **>500 QPS from one egress IP** to contact support first. Cloudflare publishes no number, only that "security scanning use-cases or proxied traffic may be rate limited" and that a high rate of uncacheable `SERVFAIL`s against one domain may be limited. We are nowhere near any of these, but cache + singleflight anyway. Also firsthand: Google returns an **HTML 400 page** (not JSON) for `type=NOTATYPE`, so decode defensively.
- **DoH JSON parameter reality.** Cloudflare's doc page documents exactly four params (`name`, `type`, `do`, `cd`); `do`/`cd` were exercised firsthand. Sending `ct`, `edns_client_subnet` and `random_padding` to Cloudflare returns a normal 200 answer w/ **no echo of them**, so whether they are honoured is unknown, treat them as Google-only. Google's `/resolve` *does* echo: `"edns_client_subnet":"0.0.0.0/0"` plus `Comment:"Response from 173.245.58.162."` (observed 2026-09-16). Both return `access-control-allow-origin: *` on a GET w/ an `Origin` header (a HEAD to Google does **not** show the header, which is a curl trap, not a CORS policy).
- **IDN.** `miekg/dns` v1.1.73 has no punycode helper; `golang.org/x/net/idna` (already transitive) does: `bücher.de -> xn--bcher-kva.de` firsthand. Display the unicode form, query the ASCII form.
- **Version pinning.** Add `github.com/miekg/dns v1.1.73` to the pinned list in CLAUDE.md + ARCHITECTURE §1, and note *why* it is pinned to v1 (v2 = different module path, pre-1.0, needs Go ≥1.27). New indirect modules: `golang.org/x/net`, `golang.org/x/sys`.
