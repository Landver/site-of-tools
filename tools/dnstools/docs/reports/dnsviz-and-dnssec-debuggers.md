# DNSViz & DNSSEC debuggers

Two free, no-account tools (across three hostnames) that do one thing a generic "dig in a box" can't: walk the **DNSSEC chain-of-trust** from root to leaf, validate every link, and explain *which* link broke. **DNSViz** (dnsviz.net, OSS CLI on GitHub) renders the chain as an annotated **Graphviz** graph & keeps a dated archive of past analyses (the UI's date picker clamps at **2020-03-12**). **Verisign Labs DNSSEC Debugger** (two hostnames, one app) renders the same walk as a **linear checklist of green/yellow/red rows** w/ hover remediation hints. They are complements, not competitors: each page literally links to the other. For a Go+htmx DNS tool they are the reference implementations of "turn an opaque SERVFAIL into a sentence a human can act on."

| **Category** | DNSSEC + delegation analyzer, graph visualizer, historical archive | DNSSEC chain-of-trust step-by-step debugger |
| **Registration** | None | None |
| **Pricing** | Free (Verisign Labs sponsored; no paid tier seen, 2026-09-16) | Free (no paid tier seen, 2026-09-16) |
| **API** | None public. Graph exports `.png/.jpg/.svg/.dot/.js` only | None. HTML only, no content negotiation |

Ran the Verisign debugger against `dnsviz.net` (37 green rows, 0 warn, 0 error), the deliberate-breakage test domain `dnssec-failed.org` (40 green, 2 warn, 2 error) & the TLD `org` (31 green, clean). Counting note: a clean run still emits one `yellow.png` + one `red.png` for the legend footer, so subtract 1 from each raw image count. Corroborated w/ `dig +dnssec @1.1.1.1 dnssec-failed.org A` -> **SERVFAIL** carrying Extended DNS Error 9, `"no SEP matching the DS found for dnssec-failed.org."`, & `dig +cd` returning the answer, which is exactly the Verisign red row "None of the 2 DNSKEY records could be validated by any of the 1 DS records." ## What they are

**DNSViz** was written by **Casey Deccio**, "originally at Sandia National Laboratories", & "Verisign Labs continues to sponsor ongoing development" (both quotes verbatim from dnsviz.net/contact/). The site's copyright footer reads "2010 - 2014 Sandia Corporation". The 2010 launch date & the 2014 hand-off to Verisign Labs are **secondhand**: Deccio presented DNSViz at DNS-OARC in Oct 2014 already badged "Verisign Labs", & the GitHub repo was created 2014-10-23. `dnsviz.net`'s own NS set is `ns1/ns2.dns-oarc.net` + UltraDNS (read off its Servers tab) & its web A record `64.191.0.138` sits in the same /24 as `ns1.dns-oarc.net` (`64.191.0.128`), so DNS-OARC hosting is likely, but nothing on the site states it. The CLI is the whole engine; the site is a Django-ish wrapper around it that is *not* published.

**Verisign DNSSEC Debugger** is a Verisign Labs "internet security tool", online since ~2011 (© footer reads 2011-2026), originally branded **DNSSEC Analyzer**. Both `dnssec-analyzer.verisignlabs.com` & `dnssec-debugger.verisignlabs.com` serve the identical app (I fetched both; both 8,435 bytes, differing only in the embedded clock). Its own "Back to Verisign Labs Tools" link is now **dead**: both it & `www.verisignlabs.com` 301 to generic verisign.com marketing pages, so no sibling-tools index survives to enumerate.

## Registration, access & pricing

No accounts, no keys, no rate-limit documentation on either. Verisign serves no `robots.txt` (404). DNSViz's `robots.txt` is `Allow: /$` + `Disallow: /`, i.e. only the homepage is crawlable, everything under `/d/` is off-limits to bots. Neither sets `Access-Control-Allow-Origin` (checked w/ `Origin: https://example.com` on both homepages **and** on DNSViz's `auth_graph.dot`), so **neither can be called from browser JS**. Verisign ignores `Accept: application/json` & returns `text/html` regardless. Any reuse is server-side scraping of HTML, against DNSViz's robots policy. The honest conclusion: **treat both as UX references, not as data sources.** (Contrast Zonemaster below, whose JSON-RPC API *is* wide-open CORS.)

## Features, complete inventory

### DNSViz web, per-domain views (4 tabs at `/d/<domain>/…`)

| View | What it gives |
|---|---|
| **DNSSEC** (`/dnssec/`) | The authentication-chain graph + Notices panel; the headline product |
| **Responses** (`/responses/`) | **Per-RRset x per-server inconsistency matrix**: fixed columns `Name | TTL | Type | Data | Status | Returned by`, then one column per authoritative NS by IPv4 **and** IPv6 (13 gTLD servers x2 for the `net` cut), cells `Y`/`N`; footer rows per server for **`RR count (Answer/Authority/Additional)`** (e.g. `2/14/27`), **`Response size (bytes)`** (e.g. `1095`) & **`Response time`**. `Status` values seen: `OK`, `VALID` |
| **Servers** (`/servers/`) | Delegation table, 7 columns: `Name | Parent zone | Child zone | Authoritative IPs | Exists? | Glue/additional records | Exists?` |
| **Analyze** (`/analyze/`) | Re-probe form w/ advanced options (below) |

Input is a domain name **or a bare IP address**: `/d/1.1.1.1/` resolves to a real archived reverse-zone analysis (runs at 2021-06-25 & 2021-11-22). `/search/` is the same entry form on its own page; `/doc/` is a one-entry documentation index pointing at `/doc/dnssec/`.

### DNSViz graph-rendering options (form on the DNSSEC tab, all GET params)

`rr` (multi) filter displayed RR types: A, AAAA, TXT, PTR, MX, NS, SOA, CNAME, SRV, NAPTR, TLSA, NSEC3PARAM, CDNSKEY, CDS, CAA · `a` (multi) filter DNSSEC algorithms 1,3,5,6,7,8,10,12,13,14,15,16 (each labelled, e.g. `13 - ECDSA Curve P-256 with SHA-256`) · `ds` (multi) DS digest algorithms 1-4 · `doe` show **denial of existence** (NSEC/NSEC3) nodes · `red` show **redundant edges** · `ignore_rfc8624` suppress algorithm-deprecation findings · `ignore_rfc9276` suppress NSEC3-parameter findings · `multi_signer` evaluate under multi-signer rules · `ta` trust anchors (root KSK checked by default, de-selectable) · free-form **additional trusted keys** textarea · `reset_query` back to defaults.

### DNSViz analysis options (Analyze tab)

`force_ancestor` re-analyze from a chosen ancestor (`.`, `net`, `<domain>`) · `extra_types` additional RR types to query · `ecs` **EDNS Client Subnet** value · `edns_diagnostics` probe servers w/ future EDNS versions/unknown options/unknown flags · **explicit delegation** (supply your own NS set, i.e. **pre-delegation testing** of a zone that isn't live yet) · `analysis_type` **authoritative servers vs recursive servers** · `perspective` **DNSViz server (me) / web client (you) / third-party (other)** · `looking_glass` pick a remote vantage point (the live list offers `as59715.net (IT)` & a US test node).

### DNSViz output & archive

Graph downloads live under the *pinned-analysis* path `/d/<domain>/<id>/dnssec/auth_graph.<ext>`: `.png` / `.jpg` / `.svg` / `.dot` / `.js` all 200 (`?download=1` forces attachment), `.json` / `.txt` / `.xml` / `.html` all 404 - **no machine-readable assessment is exposed**. Dated archive: `Update now`, `« Previous analysis` / `Next analysis »`, plus a **date picker** that snaps to the nearest analysis. The snap needs both form fields, not just the date: `?date=2024-01-15&date_search=Go+»` **302**s to `/d/dnsviz.net/ZYzBGA/dnssec/` = 2023-12-28T00:28:08Z, while `?date=…` alone is silently ignored & renders the latest run. **Archive floor:** the served picker config is `minDate: '2020-03-12'`; `?date=2020-03-12` snaps to `XmnRog` = 2020-03-12T06:07:30Z & `?date=2019-01-01` produces no redirect at all, so the public archive appears to start 2020-03-12. `?no_js=1` serves a **text-only** version that is strictly richer in prose (status rollups + full Notices list). `/doc/dnssec/` is a long illustrated legend for every shape, colour & line style.

### Verisign DNSSEC Debugger

Single input (domain name) + two advanced fields; that's the whole surface. What it does per run: validate the **root trust anchor** DS set -> fetch `./DNSKEY`, verify each DS->DNSKEY digest & the DNSKEY RRset self-signature -> follow delegation to the TLD, repeat -> follow to the zone, repeat -> then query **every authoritative NS of the target zone** for the target's `A` record & verify the RRSIG at each one. Checks observed in my two runs: DS present in parent · DS digest verifies DNSKEY · DS algorithm named (`ECDSAP256SHA256`, `RSASHA256`) · DNSKEY count · SEP/KSK identification by keytag · RRSIG count over DNSKEY RRset · RRSIG verifies DNSKEY RRset · RRSIG verifies DS RRset · each NS is authoritative · answer RR value · RRSIG count over the answer · RRSIG verifies the answer RRset. Failure findings seen on `dnssec-failed.org`: **"A DS record was found in the parent zone, but its corresponding DNSKEY was not found"** (yellow), **"Found an expired RRSIG record in the published zone data"** (yellow), **"None of the 2 DNSKEY records could be validated by any of the 1 DS records"** (red), **"The DNSSEC Chain-of-Trust is broken at this point"** (red).

Extras: **advanced options** = paste a **DS or DNSKEY as an out-of-band trust anchor** (validation then starts at that record's owner name) & supply **alternative starting name servers** (must be authoritative for the same zone as the anchor) · 4-level **progressive disclosure** · **remediation tooltips** · raw packet dumps · **bookmarkable `/<domain>` URL** · works on TLDs & subdomains as well as registrable domains.

## Record types & query options supported

Neither is a general record-lookup tool. **Verisign is fixed at `A`** for the leaf query (`/<domain>/MX` & `/MX/<domain>` both 302 away; there is no type selector). It does of course fetch DS, DNSKEY, RRSIG & NS as part of the walk. **DNSViz** probes a fixed core set by default (the `?no_js=1` rollup for `dnsviz.net` lists A, AAAA, MX, NS, SOA, CDNSKEY, CDS, plus DNSKEY/DS/NSEC per zone); the Analyze tab's `extra_types` multi-select adds exactly A(1), AAAA(28), TXT(16), PTR(12), MX(15), SOA(6), CNAME(5), SRV(33), NAPTR(35), TLSA(52), NSEC3PARAM(51), HINFO(13), CAA(257). Its `rr` filter is a *display* filter only, and offers one extra entry the probe list doesn't: NS(2). Knobs available: choose resolver (recursive mode + `-s`), choose authoritative NS (`-x`, explicit delegation), trace delegation from a forced ancestor, EDNS Client Subnet, EDNS-compatibility probing, NSID, DNS cookies, IPv4/IPv6 selection, custom trust anchors, DNSSEC & digest algorithm filters. TTLs are shown in DNSViz's node detail (`"ttl": "86400 (1 day)"`) & in Verisign's raw dumps. Neither offers a TCP toggle or a raw `dig` textual mode in the web UI.

## How it works

**Verisign = live, server-side, synchronous.** Each request re-runs the walk from a root server; the page stamps `Time: <now> UTC` & embeds every response packet. **Verified by diffing two fetches of the identical URL 28 s apart**: the second run queried `e.root-servers.net` (192.203.230.10) where the first queried `l.root-servers.net` (199.7.83.42), w/ a different query id (`8317` -> `65395`) & a different advertised `UDPSIZE` (4096 -> 1472). That rules out a cached HTML page & proves per-request wire traffic; it does not rule out reuse of an upstream resolver cache. `dnsviz.net` took **1.71 s**; the 61 KB page is one `<table>` of 137 rows. Query flow is POST-redirect-GET: `POST q=<domain>` (or `?q=<domain>`) -> **303 See Other** -> `/<domain>`. Detail level is **not** a server param (`?d=3` 303s away); `more(+)`/`less(-)` and the `+`/`-` keys toggle `display` on rows tagged `class="L0".."L3"` entirely client-side, w/ the whole L0-L3 payload shipped up front. Red/yellow severity is a `<img src="/red.png">` carrying an inline `onmouseover="tooltip.show('<p>…remediation prose…')"`.

**DNSViz = cached, re-probe on demand.** `/d/<domain>/` 302s to `/d/<domain>/dnssec/`, which renders whatever the newest stored analysis is; the *pinned* permalink carries an id, `/d/<domain>/<id>/dnssec/`. Analysis ids are **base64url of the big-endian uint32 Unix timestamp** of the run: I decoded `aqQCvA` -> `0x6aa402bc` -> `2026-09-11T13:31:40Z`, matching the page's own "Updated" line exactly, `apxm_w` -> `2026-09-05T19:01:19Z` (previous-analysis page), `ZYzBGA` -> `2023-12-28T00:28:08Z` & `XmnRog` -> `2020-03-12T06:07:30Z` (both from date-picker 302s). The graph is Graphviz on the server (`rankdir=BT`, one `subgraph cluster_<zone>` per zone, labelled w/ the zone's own analysis timestamp) rendered to PNG/JPG/SVG/DOT, plus a generated `auth_graph.js` (~90 KB for a small zone) that redraws it w/ **Raphael** & carries a `node_info` map from graph-node id -> rich JSON per node: `id`, human `description`, `algorithm`, `key_tag`, `digest_type`, `digest`, `ttl`, `status` (`VALID`), and the full list of `servers` (IPv4+IPv6) & `ns_names` that returned it. That map is what makes hovering a node useful. Re-analysis is a jQuery `$.ajax` POST back to the same URL that streams **CRLF-delimited NDJSON** on the response body; the handler sets `xhrFields.onprogress`, does `e.target.responseText.split("\r\n")`, `$.parseJSON`s every complete line, renders `{"type":"logmessage","level":…,"message":…}` into a scrolling `#progress-log`, and on `{"type":"next-location","url":…}` injects a Continue button that sets `document.location`. On a trailing `loglevel-critical` it falls back to a plain form submit. That code is **verbatim in the served analyze page**, but I did not trigger a run, so the wire behaviour is unobserved.

**The looking glass** is the distinctive bit of plumbing. `dnsviz probe -u/--looking-glass-url <url>` issues the diagnostic queries *from somewhere else* over HTTP(S) or SSH, so the probe's source address is the looking glass, not you. `contrib/` in the repo ships three implementations: `dnsviz-lg.cgi` (CGI), `dnsviz-lg-ws.js` (WebSocket), `dnsviz-lg-java/` (Java). The web form offers two vantage points, `as59715.net (IT)` -> `http://dnsviz.as59715.net/dnsviz-lg.cgi` & `dnsviz.net (US) (test)` -> `http://dnsviz.net/lg/` (200). The "Web client (you)" perspective is the Java one, and it is **effectively dead**: the page calls `dtjava.embed()` from `http://java.com/js/dtjava.js` (that script does still serve, 40 KB) against `/static/applet/dnslookingglass.jnlp`, which is an `<applet-desc main-class="net.dnsviz.applet.DNSLookingGlassApplet">` requiring `j2se 1.6+` & `<all-permissions/>`. The file & the loader are live; browser NPAPI applet support that could run it is not, so I could not test it end to end. This is how you answer "is it broken *for me*, or broken everywhere?" without a global probe fleet.

## Output & UX

**Verisign** is a flat vertical checklist, one row per assertion, a coloured dot at the left, plain-English claim at the right, nested raw evidence hidden underneath. No summary header, no score, no counts; you read top to bottom & look for the first non-green. Empty/invalid input re-renders the form. Ends w/ two nice touches: a legend line ("Move your mouse over any ⬤ or ⬤ symbols for remediation hints") & a **cross-link to the competitor**, "Want a second opinion? Test dnsviz.net at dnsviz.net."

**DNSViz** leads w/ the graph & a right-rail **Notices** box. The `?no_js=1` view exposes the underlying assessment as three status rollups, `RRset status: Secure (7)` listing `dnsviz.net/A … /SOA`, `DNSKEY/DS/NSEC status: Secure (10)` listing `./DNSKEY (alg 8, id 20326)` style entries, `Delegation status: Secure (2)` listing `. to net`, `net to dnsviz.net`, then `Notices -> Warnings (2)` w/ prose + **RFC citations**: "dnsviz.net/CDNSKEY: The contents of the DS RRset are inconsistent with those of the CDNSKEY RRset. See RFC 7344, Sec. 3, RFC 7344, Sec. 5." Three node statuses only: **secure** (blue outline), **bogus** (red), **insecure** (black). Delegations get their own vocabulary: insecure (black solid), **lame** (yellow dashed), **incomplete** (yellow dashed), secure (blue solid), bogus (red dashed). Result URLs are permanent & shareable because they name a specific archived analysis.

## Monetization, limits & abuse controls

Neither monetizes, as far as either site says: no credits, no tiers, no keys, no published quotas, no ToS page found on either, checked **2026-09-16**. This is absence of evidence, not a guarantee - assume an undocumented ceiling exists on both. DNSViz's controls are indirect: results are cached so the expensive path (a full probe) needs an explicit click, `robots.txt` bans crawling `/d/`, and the analyze endpoint streams progress rather than holding a request open. Verisign's control is that the tool is cheap (one A-record walk, 1.7-2.8 s observed) and offers nothing bulk-shaped. Both are frame-protected (DNSViz `X-Frame-Options: SAMEORIGIN`, Verisign `DENY` + `X-Content-Type-Options: nosniff`) & CORS-closed. Both run Apache.

## Ideas worth stealing

- **Severity dot + claim + collapsed evidence, in `<details>`.** Verisign's row is `[dot] "RRSIG=41136 and DNSKEY=41136 verifies the A RRset"` with the raw packet in a nested, hidden row. In Go: render every finding as a struct `{Severity, Claim, Evidence []string}` and a `<details><summary>` per row. Zero JS.
- **One global detail slider, not per-row toggles.** Tag every row `level 0..3`, ship all of them, and let `+`/`-` (or a 4-stop segmented control) show levels `<= n`. Verisign does this with a 30-line script & no server round trip; in Alpine it is `x-data="{lvl:0}"` + `x-show="row.lvl <= lvl"`. Far better than "expand all" because level 3 is raw wire data nobody wants by default.
- **Findings as a table of definitions, not `fmt.Errorf` strings.** DNSViz's `dnsviz/analysis/errors.py` is **240 classes / 155 distinct `code` values / 10 top-level categories** (`RRSIGError`, `DSError`, `NSECError`, `ResponseError`, `DelegationError`, `CDNSKEYCDSError`, `DNAMEError`, `DNSKEYError`, `TrustAnchorError`, `ZoneDataError`), and **161 of them carry `references`**. Each one is `code = 'EXPIRATION_IN_PAST'`, `description_template = "The Signature Expiration field of the RRSIG RR (%(expiration)s) is %(expired_time)s in the past."`, `references = ['RFC 4035, Sec. 5.3.1']`, `required_params = [...]`. Port the *shape*: a `var findings = map[Code]Finding{...}` in the domain package, templated description, RFC links rendered as anchors. It makes the tool feel authoritative & it keeps the copy out of handlers, which is golden rule #1 anyway.
- **Cite the RFC section inline, always.** "See RFC 7344, Sec. 3" next to a warning is the single cheapest credibility upgrade on the page.
- **POST-redirect-GET to a clean `/<domain>` URL.** Verisign's `303` to `/<domain>` makes every result bookmarkable & shareable w/ no query-string noise. Trivially htmx-compatible via `HX-Push-Url`.
- **Three-way status vocabulary, not a pass/fail boolean.** `secure` / `insecure` / `bogus` is the correct DNSSEC model & most tools get it wrong by conflating "unsigned" with "broken". Separate `lame` / `incomplete` for delegations.
- **The Responses matrix.** RRs down, authoritative servers (both address families) across, `Y`/`N` cells, plus response time / size / RR counts per server. This is the single highest-value view neither a `dig` wrapper nor a propagation checker gives you, and it is pure server-side HTML: query each NS once, pivot, render a table. Strongest differentiator on this list for a small tool.
- **Parent vs child delegation diff.** DNSViz's Servers tab is 7 columns: NS name, parent zone, child zone, authoritative IPs + `Exists?`, glue/additional records + `Exists?`. Catches the most common real-world breakage (stale glue, NS set drift) & needs two queries.
- **Base64url-of-uint32-timestamp as the permalink id.** Short, opaque-looking, sortable, and decodable back to the analysis time w/ no database lookup. Fits the existing Mongo lookup-history feature: store a run, link to `/d/<domain>/<b64ts>/`. (Caveat if you copy the pattern: uint32 overflows in 2106, and the id leaks exact run time, which is fine here & not always.)
- **Stream the probe as NDJSON log lines.** DNSViz streams `{"type":"logmessage","level":…,"message":…}` per line & ends with a `next-location`. In Go + htmx the idiomatic equivalent is SSE with one `<div>` swap per event, then an `HX-Redirect`. Makes a 10-second multi-server probe feel alive instead of hung.
- **Nearest-analysis date picker.** `?date=YYYY-MM-DD` + a 302 to the closest stored run (2024-01-15 -> 2023-12-28) is a two-line Mongo query & turns a history list into a time machine. Do redirect to the pinned id rather than rendering in place, so the result stays shareable.
- **Cross-link your competitor.** "Want a second opinion? Test X at Y." Costs nothing, buys trust, and both of these tools do it to each other.
- **Ship the legend as a real page.** `/doc/dnssec/` explains every colour & shape in prose. Any non-obvious iconography needs one.

## Gaps & what they do not do

No JSON/REST API on either (DNSViz's `.dot` & `auth_graph.js` `node_info` blob are the only structured exports, and neither is documented as an interface). No CORS, so no browser-side reuse. Verisign is **A-record only** for the leaf query (`/<domain>/MX` & `/MX/<domain>` both 302 back to the form), single-domain, no bulk, no history, no permalink to a *past* result (the URL re-runs). DNSViz is **cached by default**, so a fresh breakage needs a manual re-analysis; its archive only reaches back to 2020-03-12; & its "Web client (you)" perspective depends on a **Java applet no current browser can load**. Neither does email auth (SPF/DKIM/DMARC), blocklists, WHOIS/RDAP, propagation-across-public-resolvers, reverse/passive DNS, reputation, or monitoring/alerting. Neither offers DoH/DoT/DoQ transport testing: `dnsviz probe`'s option list has no such flag, & its `-u` looking glass uses HTTP(S)/SSH as transport for the *looking-glass protocol*, not DNS-over-HTTPS. DNSViz's web copyright footer still reads "2010 - 2014 Sandia Corporation" & the CLI's last release is **v0.11.1, 2025-04-21**, though `master` was pushed 2026-09-12: maintained, not fast-moving.

## Open source / reusable

`github.com/dnsviz/dnsviz`, **GPL-2.0-or-later** (the repo's `COPYRIGHT` says "version 2 of the License, or (at your option) any later version"; PyPI's classifier agrees, GitHub's auto-detector just labels it "GPL-2.0"), **1,247 stars / 162 forks**, latest release v0.11.1 (2025-04-21), `master` pushed 2026-09-12, Python (dnspython, pygraphviz, cryptography). Contains the entire engine: `probe` / `grok` / `graph` / `print` / `query`, the error taxonomy, the Graphviz layout, `share/trusted-keys` & `share/hints`, plus `contrib/` w/ the three looking-glass servers (`dnsviz-lg.cgi`, `dnsviz-lg-ws.js`, `dnsviz-lg-java/`) & `digviz`. **The dnsviz.net web front-end is not in the repo** (root is `bin contrib dnsviz doc external share tests` + packaging) so the page design has to be reimplemented; the *data* is one `dnsviz probe … | dnsviz grok -o -` pipe away. Copyleft matters if you ever vendor code rather than shell out. The Verisign debugger is closed source w/ no reusable component. Adjacent & worth knowing: **Zonemaster** (`zonemaster.net`) is OSS and, unlike these two, exposes a real unauthenticated **JSON-RPC API** - `POST https://zonemaster.net/api` w/ `{"jsonrpc":"2.0","id":1,"method":"version_info"}` returned `{"zonemaster_engine":"v9.0.0","zonemaster_backend":"12.1.1","zonemaster_ldns":"5.1.0"}` on 2026-09-16, and it answers w/ `Access-Control-Allow-Origin: *`, so it is callable straight from browser JS as well as from Go. That makes it the realistic upstream if the owner wants DNSSEC + delegation findings without running Python.
