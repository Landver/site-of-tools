# check-host.net & ping.pe

Two long-running, hobbyist-run **multi-vantage-point network checkers** from the hosting/LowEndTalk world. Neither is a DNS tool proper: both answer *"is it just me, or is it broken from over there too?"*, & both bolt a thin-to-real DNS check onto a ping/HTTP/TCP/traceroute core. They matter here for one reason each. **check-host.net** hands out its entire vantage-point inventory & every check result as **keyless JSON over plain HTTP GET** — no account, no token, no quota page — which is the cheapest possible path to a real propagation map for a Go backend. **ping.pe** pairs a stated design philosophy of *fewer, single-homed* nodes with a firsthand-confirmed live fleet of **166 single-homed Tier-1/Tier-2 vantage points across ~45 countries** — a scale the site's own marketing undersells and older third-party write-ups understate.

- **URL:** https://check-host.net/check-dns · https://ping.pe/ · **Category:** multi-node reachability checkers w/ a DNS side-feature · **Registration:** none on either · **Pricing:** free, ad-funded · **API:** check-host yes (documented, keyless); ping.pe none published, but a real internal JSON API exists (see below).
- **Firsthand check (2026-09-16):** check-host probed hard — `GET /nodes/hosts` w/ `Accept: application/json` returned **56 nodes across 34 countries**, each w/ country/city/IP/**ASN**; submitted keyless `check-dns`, `check-ping`, `check-http`, `check-tcp`, `check-udp` & undocumented `check-traceroute` jobs & polled every result, incl. a punycode-domain job that resolved correctly end-to-end; read their minified `chbase.js` for the polling & CSRF mechanics; confirmed **no CORS** (`OPTIONS` -> **403**, no `Access-Control-Allow-Origin` on `GET` w/ `Origin:`). ping.pe's tool pages sit behind a plain JS interstitial (sets an `antiflood` cookie, redirects to `?browsercheck=ok`) — not a CAPTCHA or login. Replaying that cookie's value, which the page itself serves in cleartext to every visitor, reached the real result pages, so this pass adds firsthand data: `dig.ping.pe` submitted via its actual `ajax_startTask_v1.php`/`ajax_getPingResults_v2.php` JSON endpoints, returning real per-node dig output & a server-reported **`pinger_count: 166`**. Its `/about` & `/contact` were already ungated.

## What it is

**check-host.net** — online since 2010, Russian/English UI, run anonymously behind Cloudflare, funded by hosting ads. Six public tools (IP info, Ping, HTTP, TCP, UDP, DNS) plus a subnet calculator, a hidden traceroute page & a free 15-minute throwaway Linux/Windows web terminal. Nodes are **donated VPSes**: the FAQ's sponsor spec is tiny (KVM/Xen/VMware/HyperVM/OpenVZ, Debian 13/12, IPv4 + IPv6, ≥256 MB RAM, ≥5 GB disk, ≥100 GB bandwidth), which is why the fleet skews to whoever donates. As of 2026-09-16 that skew is stark: **Iran 7 nodes, USA 5, Germany 3, Ukraine 3**, 2 each for Indonesia/Israel/Netherlands/Russia/Spain/Sweden/Switzerland/Turkey, 1 each for 22 others. Nobody else gives you 7 Iranian vantage points keyless, & for censorship/GFW-style questions that is the whole value.

**ping.pe** — a one-person project running since 2015 (firsthand, `/about`: "Since 2015 ping.pe had seen tremendous growth… I re-wrote its code multiple times"). Contact is a Gmail address, registrant is privacy-protected via 1API GmbH, DNS on Cloudflare. Its node policy is a deliberate, argued inversion of check-host's: it **refuses** to add more VPS endpoints because "most VPS/Cloud providers are T3 multihomed networks… which reduces the diagnostic value", & only wants VMs **single-homed to a T1/T2 IP transit provider** (2 GB RAM, 2 cores, 15 GB disk, Rocky/Alma 9, 10 Mbit uplink). That is a real product thesis: a multihomed probe averages away the transit fault you are hunting. The "few nodes" framing in `/about` is about node *type*, not node *count* — a firsthand `dig` job against `example.com` today (2026-09-16) got a server-reported `pinger_count: 166`, spanning the US (30+), Bangladesh (13), China (13), Turkey (9), India (6), GB (6) & dozens more single-country nodes; the "~30, mostly NA & China" figure floating around older hosting-forum threads is stale.

## Registration, access & pricing

Neither service has accounts, keys, tiers or a pricing page. check-host's FAQ states the API "is available for check requests" & that the **"IP info" API is not available at this time** (checked 2026-09-16). Revenue on both is display advertising; check-host additionally sells the ad slot policy publicly ("We do not place advertisement of IP-stressers, booters and etc.").

## Record types & query options supported

This is where check-host falls over as a DNS tool, but ping.pe does not. check-host's `check-dns` returns **A, AAAA and TTL only**, plus **PTR** if you feed it an IP. I tried `&type=MX&resolver=8.8.8.8` (confirmed again this pass, incl. polling the resulting job): both params are **silently ignored**, the job ran as a plain A/AAAA lookup. There is no MX/TXT/NS/SOA/CNAME/CAA/SRV, no resolver selection, no authoritative-vs-recursive switch, no `+trace`, no TCP/EDNS/ECS/DO-bit knob, no raw wire output, no NXDOMAIN-vs-SERVFAIL distinction (a bogus domain simply returns `{"A":[],"AAAA":[],"TTL":null}`). Each node just asks **its own box's system resolver**, which is exactly the property you want for "what do real users in Tehran get" & exactly wrong for "what does the zone actually say".

**ping.pe's `dig.ping.pe`, verified firsthand this pass, is a real multi-type DNS tool**: query syntax `dig HOST:TYPE:NAMESERVER`, TYPE ∈ **A, AAAA, CNAME, TXT, MX, NS, PTR, CAA, SOA** (default `A`), NAMESERVER is any resolver IP (default `8.8.8.8` — i.e. it asks a **caller-chosen recursive resolver**, not each node's own system resolver, the opposite tradeoff from check-host). A live job against `example.com` returned per-node zone-format rows w/ per-query latency, e.g. `example.com. 300 IN A 172.66.147.243 [32 ms]`. No DNSSEC/raw-wire/`+trace` support was observed or advertised in the help text, and only one NAMESERVER can be set per query (no side-by-side resolver comparison in one job).

## How it works

**check-host: fully server-side, async job + poll.** `GET /check-<type>?host=&max_nodes=&node=` w/ `Accept: application/json` immediately returns `{ok, request_id, permanent_link, nodes}` where `nodes` maps node hostname -> `[cc, country, city, ip, asn]`. Results arrive out of order at `GET /check-result/<id>`; a node that has not answered yet is `null`, a node that answered w/ nothing gets empty arrays. `GET /check-result-extended/<id>` wraps the same payload w/ `{command, created (unix ts), host}` — results are **stored & replayable**, which is what makes `permanent_link` work.

Their own UI does not use the documented endpoint. `chbase.js` POSTs to an **underscore** sibling, `POST /check_result/<id>`, form-encoded, w/ a repeated `slaves[]=<node>` list — and it **splices each node out of that list as it reports**, so every subsequent poll asks only for stragglers. Cadence, straight from the source: first poll after **1000 ms**, then **3000 ms** between tries, **max 20 tries** (~58 s), after which unreported nodes are rendered as failed. A second loop, `analyze_results_watcher`, polls at 1 s for up to 30 tries & fires a handler once the share of nodes returning one of `["Connection reset by peer","Operation timed out","Connection timed out","Broken pipe","Server error","No route to host"]` crosses a caller-supplied `fail_percent` — i.e. "your site looks down from most of the world" is a first-class, thresholded event, not a thing the reader has to eyeball.

**Content negotiation is the front door.** Same URL, two representations: `Accept: application/json` -> the API; no header -> HTML. The HTML branch is CSRF-guarded — `GET /check-dns?host=example.com` w/o a token returns a **555-byte auto-submitting form** that injects `csrf_token` & re-GETs. The JSON branch skips CSRF entirely. Note the consequence: **the anti-abuse shim guards only the browser path.**

**ping.pe: server-side job + JSON poll, now confirmed firsthand.** jQuery 2.3.1, no framework, self-hosted **Matomo** at `matomo.ping.pe` (siteId 2) rather than Google Analytics. The *entry* shell is a **byte-identical 10,591-byte page** across `mtr`, `dig`, `tcp`, `port`, `bgp-lg` & `www` (re-verified this pass) — but that shell is not the whole mechanism; I could not find `location.hostname` anywhere in it, so the earlier guess that mode-selection happens purely client-side from the hostname does not hold up. What's actually observable: submitting a query (`POST /` from the search box, or the subdomain itself, e.g. `dig.ping.pe/<subject>`) renders a **command-specific results page** (confirmed different HTML per subdomain: `ping.pe/8.8.8.8` is 571 KB, `mtr.ping.pe/8.8.8.8` is 230 KB, `dig.ping.pe/example.com` is 131 KB) carrying a signed, single-use `taskStartToken` (a JWT-shaped blob embedding `page_kind`, `query`, `origin`, `ip`, `ua`-hash, `exp` & a `nonce`, base64+HMAC-style signature). That token is POSTed once to `ajax_startTask_v1.php` w/ the query string; the response includes `stream_id`, `pinger_count`, & the parsed `command`/`target_type`/`target_nameserver`. Results are then polled via `GET ajax_getPingResults_v2.php?stream_id=<id>`, `interval_s` (2–60 s, default 5) between polls, **max 20 tries** — the same cadence-cap check-host uses independently. On tab close, `GET ajax_stopTask.php?stream_id=<id>` tears the job down. The gate itself is a plain JS shim, not a CAPTCHA: `document.cookie="antiflood=<hex>;max-age=86400"` then `location.replace(href + '?browsercheck=ok')` — the cookie value is served to every visitor in cleartext, so it is a flood-pacing nudge, not an access control; the real anti-abuse is the signed, IP/UA/origin/exp-bound start token plus a server-side `too_many_active_tasks` concurrency cap surfaced in the JSON error path. `robots.txt` is fully permissive.

## Output & UX

check-host's result page is a three-column table: **Location | Result | TTL**. Each row's location expands to a card carrying **Node hostname, IP, Datacenter, ISP, AS number** w/ a link out to bgp.tools — note *Datacenter* ("Scaleway DC2", "Tornado Datacenter", "Gedung Cyber") is richer than anything `/nodes/hosts` returns. Above the table: host + check type, permanent link, Twitter share, `Checked on Wed Sep 16 08:57:39 UTC 2026`, and a **Check again** button. Below: the embedded live terminal & an ad.

The clever part is that the **permanent report and the live check share one renderer**. The report page ships the stored results inlined as literal JS calls:

```
check_displayer.display("id2.node.check-host.net", [{"TTL":32,"A":["8.47.69.0",…],"AAAA":[…]}]);
```

— the exact same `DNSCheckResultDisplayer.display(node, payload)` the poller calls per arriving node. One fragment renderer, two feeds: live poll, or replay from storage. Cost of that choice: the shared link is **JS-required** (the page literally prints "Enable JavaScript support"), so no-JS & scrapers get nothing, and `robots.txt` `Disallow: /check-report/` keeps reports out of search.

Empty/error states are explicit & documented per check type: ping `[[null]]` = node could not resolve the name; HTTP `[[0, 0.07, "No such device or address", null, null]]` = network error; TCP `[{"error":"Connection timed out"}]`; UDP "Open or filtered" is stated in the FAQ to be **correct, not a bug**. There are no export formats (no CSV/JSON download button in the UI), no charts, no history.

ping.pe's output, firsthand: a black-background monospace (Roboto Mono) table, 66 px numeric columns / 140 px+150 px for the first two, dark-only (`color-scheme: dark` hard-set). Columns are **Geo | ISP | Loss | Sent | Last | Avg | Best | Worst | StDev | MTR▼ | Chart**; result cells render empty in the initial HTML & are filled in by the `ajax_getPingResults_v2.php` poll, so the page is a shell until JS runs (confirmed: the 166 rows are pre-rendered w/ per-node Geo/ISP/IP but blank metrics). MTR expands per row via a `.mtr-toggle` click that flips `display` on a sibling row keyed by `data-pinger-id`, w/ an "expand all" toggle. **"Save as image"** (`html2canvas` over `#page-div`, POSTed to `save_image.php`, served from `i.ping.pe`) and **"Save snapshot"** (a frozen static-HTML copy of the results, POSTed to `save_snapshot.php`, served from `s.ping.pe`) are two distinct export paths, not one.

## Monetization, limits & abuse controls

Ads only, both. check-host runs a "Offshore Cloud Services" banner, an offshore/DMCA-ignored host (ava.hosting), a registrar (LuxHost) & dedicated-server ads (Serv.Host), with per-ad dismissal wired to `GET /close_ad/<id>` + a `closey_advertisments` cookie, and the terminal sponsored by h2.hexus. It cross-promotes an affiliated lite IP API, IPiz.net. No published rate limits, no 429 documented, no key; abuse control is the browser-path CSRF shim, Cloudflare in front, `robots.txt` disallowing `/check-report/` & `/check-http?host=*`, and a stated refusal of booter/stresser advertising. ping.pe's control is layered deeper than a single cookie: the cleartext `antiflood` cookie + `browsercheck` redirect only paces naive scripted requests, while the actual submission path requires a signed `taskStartToken` bound to origin/IP/UA-hash/expiry/nonce, and the start endpoint can return a `too_many_active_tasks` error — a concurrency cap, not a request-count quota, and its threshold is unobserved. I made roughly two dozen total check submissions across both services this report & the prior pass combined & hit no hard rate limit on either; **do not read that as "unlimited"**, only that the limit (or the concurrency cap, on ping.pe) is above that count.

## Ideas worth stealing

- **Steal the vantage-point metadata feed outright.** `GET https://check-host.net/nodes/hosts` is keyless, 1.6 KB gzipped, and gives `{hostname: {asn, ip, location:[cc,country,city]}}` for 56 probes. Cache it in Mongo w/ a TTL index (you already have `platform.EnsureTTLIndex`), refresh daily, and a propagation UI gets country flags + city + **ASN** labels for free — metadata Globalping et al. mostly gate behind a key.
- **No CORS means the proxy is mandatory, and that is fine.** `OPTIONS` -> 403, no `ACAO`. So the fetch lives in a Go repository below the domain service, exactly per rule #5, and the browser never talks to check-host. Removes the "should this be client-side?" debate before it starts.
- **Copy the async shape: submit -> `request_id` -> poll, narrowing the poll set.** Their poller drops each node from `slaves[]` the moment it answers. In htmx terms: one `hx-get` on `/dns/propagation/<id>?pending=de1,fr2,…` w/ `hx-trigger="load delay:1s, every 3s"`, returning an OOB fragment per settled node & a shrinking pending list; when the list empties, return a response w/o the trigger and polling stops by itself. No WebSocket, no SSE, ~20 lines of handler.
- **Their timing constants are a free tuning starting point:** first poll at 1 s, then 3 s, give up at 20 tries. Battle-tested against a fleet whose slowest members are 256 MB donated VPSes.
- **Thresholded verdict, not just rows.** `analyze_results_watcher` + the fixed `condition_err_msgs` list turns N rows into one sentence. A DNS analogue: count nodes whose answer set differs from the modal answer set, and if >X% disagree, render a single "**Not converged: 12 of 40 vantage points still see the old A record**" banner above the table. That one line is the actual product.
- **One renderer, two feeds.** Make the per-node result fragment a single Go template; feed it live from the poll handler and from stored Mongo results on `/dns/report/<id>`. Their `check_displayer.display(node, payload)` inlined into a saved page is the same idea, minus their JS-required tax — server-render yours and the shared link works without JS.
- **`check-result-extended` is the right envelope.** `{command, created, host, results}` — the stored record carries *what was asked & when*, not just the answer. Cheap to copy into a Mongo doc; makes "Checked on \<UTC\>" + "Check again" trivial.
- **Per-node provenance popover.** Node hostname, IP, **datacenter**, ISP, ASN, plus an outbound link to bgp.tools. Answers "why does this node disagree?" in one hover and costs one join against cached node metadata.
- **"Save as image" (ping.pe).** html2canvas over the results div gives a paste-into-a-ticket artifact. It is vendored JS, no npm, fits rule #3. Higher perceived value than a CSV nobody opens.
- **Show the data's age, per source (check-host IP info).** Five geo DBs side by side, each stamped with its own snapshot date. Your IP tool already fuses IP2Location + Shodan + blocklists; stamping each card with its source & vintage is the same honesty mechanic and costs a line.
- **ping.pe's node thesis, applied to DNS:** fewer, better-chosen vantage points beat many. For DNS the analogue is not transit tier, it is **resolver diversity** — one node each behind Google/Cloudflare/Quad9/OpenDNS/a national ISP resolver tells you more than 40 nodes all behind 8.8.8.8. Say so in the UI.
- **Undocumented-but-live endpoints are a hint, not a promise.** `/check-traceroute` works & is unlisted; so do ping.pe's `ajax_startTask_v1.php`/`ajax_getPingResults_v2.php`, driving a full UI with zero public docs. Useful to you; also a reminder to version your own JSON before anyone depends on it.
- **A signed, short-lived start token beats a plain CSRF form (ping.pe).** Binding the submit token to origin/IP/UA-hash/expiry/nonce server-side, rather than check-host's bounce-and-reinject form, stops replay from a different origin without an extra round trip on the happy path. Worth copying if `/dns/propagation` ever needs stronger abuse resistance than the htmx polling shape alone gives it.

## Gaps & what it does not do

**check-host** has no RR types beyond A/AAAA/PTR, no resolver choice, no authoritative query, no delegation trace, no DNSSEC anything, no EDNS/ECS, no TCP fallback, no raw output, no NXDOMAIN/SERVFAIL/REFUSED distinction, no IPv6-only vantage selection & no way to ask a node which resolver it actually used. Its fleet balance is donation-driven, not designed: 7 Iranian nodes & 1 Brazilian is great for one question and useless for another, and there is no LATAM/Africa coverage to speak of.

**ping.pe's `dig` is more capable than check-host's DNS check** (9 record types, caller-chosen resolver) but still has no DNSSEC, no raw wire output, no `+trace`/delegation walk, and only one resolver per query (no side-by-side comparison in a single job). Neither tool does email-DNS checks (SPF/DKIM/DMARC/MX health), zone health audits, reverse/passive DNS, reputation/blocklist lookups, subdomain enumeration, or domain WHOIS/RDAP (check-host does IP WHOIS only). Neither has monitoring, alerting, scheduled re-checks, history/diff between runs, or webhooks; check-host has no UI export at all, ping.pe has image & static-snapshot export but no CSV/JSON download. ping.pe publishes no *official* API or docs — the JSON endpoints above are unannounced & could change without notice — and no uptime guarantee; it is one person's project with a Gmail contact.

## Open source / reusable

Neither service publishes its own code. check-host does list **eight** third-party API clients on its docs page, incl. a Go one: `d1manpro/checkhost` (Go), `tbdsux/check-host` (Rust), `diasnull/check-host` (Python), `und3f/checkhost-client-ruby`, `ILYAGVC/CheckHostPHP` & `alirezax5/checkHost` (PHP), `FlorianMichael/CheckHost4J` (Java), `Lifailon/Check-Host` (PowerShell). Given the API is five GET endpoints & one JSON shape, writing 60 lines of Go against it directly is likely cleaner than taking a dependency — but the clients are useful as a cross-check on response edge cases. `html2canvas` (MIT) is the reusable piece behind ping.pe's image export & vendors fine under `shared/static/js/`.
