# Record type reference — what to support and why

Which RR types a DNS lookup tool should query, decode & render, and which are safe to skip. The decision this informs is not "do we support DNSSEC" but three cheaper ones: **how long the type list is**, **how much of the rdata we decode vs print raw**, and **whether we take a DoH JSON upstream or parse wire format ourselves**. The last one is settled by a firsthand finding below: the two free DoH JSON APIs decode *different, partial* slices of the long tail and neither covers it, so a type list past ~20 entries forces `miekg/dns`.

- **Scope:** every RR type a user might plausibly ask for, plus the TXT-carried conventions (SPF, DKIM, DMARC, BIMI, MTA-STS, TLS-RPT, verification tokens) that are not types at all but are what most lookups are really after. · **Why it matters for our build:** a type the tool cannot ask for is a feature that never ships, and a type it asks for but renders as hex is worse than not offering it.
- **Firsthand check (2026-09-15, re-verified & corrected 2026-09-16, adversarial fact-check pass same day):** ~90+ `dig` queries against `1.1.1.1`/`8.8.8.8` covering 35+ RR types, incl. the live demo zone `*.dns.netmeister.org`; decoded real `ech=` SvcParam blobs byte-by-byte in Python; decoded the root zone's ZONEMD rdata byte-by-byte; compared `dns.google/resolve` vs `cloudflare-dns.com/dns-query` rendering of ~20 types; CORS-probed both with a real GET (not just `HEAD`, which silently hides Google's CORS header); measured type prevalence across 25 apex domains; pulled the IANA RR-type CSV & the SvcParamKeys registry, recounted its rows & obsolete list directly; read RFC 9460/9848/9849/9824/9859/9606/8482/7208; fetched Google Admin Toolbox's `dig` page HTML directly and counted its 17 literal `value="…"` type tokens (this is now firsthand, not secondhand — see "Verified firsthand" below); re-probed NsLookup.io's `www.nslookup.io/api/v1/records` endpoint live and found it working, contra an earlier claim that it 404s; counted DigWebInterface's live type `<select>`; counted NsLookup.io's per-type lookup pages; grepped & recounted `miekg/dns` `TypeToRR` directly off `ztypes.go` (80, not 81).

## The mechanics

**The registry is small and mostly dead.** IANA's `dns-parameters-4.csv` has **111 data rows** (112 lines incl. header); 8 are explicitly OBSOLETE/DEPRECATED (`MD`, `MF`, `NSAP`, `NSAP-PTR`, `NXT`, `A6`, `MAILA`, `DLV`). Codes are sparse & non-contiguous: `SVCB`=64, `HTTPS`=65, `SPF`=99, `NXNAME`=128, `URI`=256, `CAA`=257. Practically, **~20 types carry ~99% of real lookups** and the rest are a long tail you offer for completeness.

**Presentation format is a per-type decoder, not a formatting rule.** Wire rdata is opaque bytes. RFC 3597 defines the fallback for a type your software does not know: `\# <length> <hex>`. Every rendering decision downstream follows from whether *your* code has a decoder for that type. macOS system `dig` (**DiG 9.10.6**) is the cautionary example: `dig cloudflare.com HTTPS` does **not** error, it silently parses `HTTPS` as a *second query name* and sends `cloudflare.com IN A` + `HTTPS IN A` (both QUESTION sections observed). Same trap for `ZONEMD`, `SVCB`, `NXNAME`, every mnemonic newer than the binary. `dig cloudflare.com TYPE65` works but returns RFC 3597 hex.

**Underscore prefixes are the single biggest UX trap.** RFC 8552 ("Attrleaf") scopes records to a service by prefixing the owner name. A plain `domain + type` form returns NODATA for **SRV, TLSA, SMIMEA, OPENPGPKEY, URI, SVCB, DMARC, DKIM, MTA-STS, TLS-RPT** because the record does not live at the apex. `TLSA` lives at `_25._tcp.mail.ietf.org`, DMARC at `_dmarc.example.com`, DKIM at `<selector>._domainkey.example.com`. RFC 9460 **§9.1** carves out **HTTPS** as the deliberate exception: no underscore for port 443 (so it works at the apex, with wildcards & behind CNAME chains), but Port Prefix Naming (§2.3) elsewhere, e.g. `_8443._https.example.com`.

**TXT is a bus, not a type.** Apex TXT is where a dozen unrelated protocols park. Sampling four apexes firsthand turned up SPF, Microsoft `MS=`, Salesforce `00D…`, `TAILSCALE-`, `adobe-idp-site-verification=`, `anthropic-domain-verification-…`, `apple-domain-verification=`, `atlassian-domain-verification=`, `aws-domain-control-verification=`, `_globalsign-domain-verification=`, `amazonses:`, `VISA=`, `citrix-verification-code=`, `canva-site-verification=`, `cursor-domain-verification-…`. Rendering apex TXT as an undifferentiated list of quoted strings is the default everywhere & is the cheapest thing to beat.

**DNSSEC types only appear if you ask.** `RRSIG`/`NSEC`/`NSEC3` come back only w/ the EDNS **DO bit** set (`dig +dnssec`). They arrive in the *authority* section on negative answers, not the answer section. Cloudflare's NSEC for a nonexistent name reads `\000.nonexistent-zz9-test.cloudflare.com. RRSIG NSEC TYPE128` (observed) — "compact denial of existence" (RFC 9824, Sept 2025), where **TYPE128 = NXNAME**, a type newer than the resolver printing it.

**SVCB/HTTPS & ECH are the 2026 story.** `HTTPS` (65) & `SVCB` (64) are one wire format w/ two modes: **AliasMode** (`SvcPriority 0`) which finally gives apex aliasing CNAME cannot, and **ServiceMode** (priority > 0) carrying key=value SvcParams. Registered keys, read off the IANA SvcParamKeys registry: `mandatory`(0) `alpn`(1) `no-default-alpn`(2) `port`(3) `ipv4hint`(4) **`ech`(5, now RFC 9848)** `ipv6hint`(6) `dohpath`(7, RFC 9461) `ohttp`(8, RFC 9540) `tls-supported-groups`(9, draft) `docpath`(10, RFC 9953) `pvd`(11, `RFC-ietf-intarea-proxy-config-13`, in the RFC Editor queue) `oots`(12, draft). **RFC 9849 "TLS Encrypted Client Hello" and RFC 9848 "Bootstrapping TLS Encrypted ClientHello with DNS Service Bindings" are both Proposed Standard, March 2026** — `ech=` is no longer a draft artifact.

**ECH decoding, the actual bytes.** `crypto.cloudflare.com`'s `ech=` is 96 base64 chars decoding to **71 bytes**. Decoded firsthand: 2-byte `ECHConfigList` length (69), then one `ECHConfig` w/ **version `0xfe0d`**, a rotating `config_id` (**51** on 2026-09-16, **124** the day before, so never pin it), `kem_id=0x0020` (DHKEM X25519-HKDF-SHA256), 32-byte public key, one cipher suite (`kdf=0x0001` HKDF-SHA256, `aead=0x0001` AES-128-GCM), `maximum_name_length=0`, and **`public_name="cloudflare-ech.com"`**. `defo.ie` publishes a 194-byte list of **3** configs, all `public_name=cover.defo.ie`. That public name is the SNI the client sends in the clear, i.e. the one field a human reading an ECH config actually wants. ~70 lines of Go. **Nothing on the shelf renders it.**

**Consensus floor:** `A AAAA CNAME MX NS SOA TXT` (7, everyone). **Consensus ceiling for consumer tools:** + `PTR SRV CAA DS DNSKEY` (12). **HTTPS/SVCB is the live dividing line in 2026:** both Google front ends, DigWebInterface & NsLookup.io have it; MXToolbox, DNSChecker & whatsmydns do not. Nobody decodes `ech=`.

## The type inventory

Prevalence column marked **[s]** is my own 25-domain apex sample (2026-09-15, well-known brands, biased toward technical operators, **not** a census).

### Tier 1 — the seven everyone ships

| Type (code) | What it is | Why looked up | How rendered | Common |
|---|---|---|---|---|
| **A** (1) | IPv4 address | "where does this point" | plain IP, usually + geo/ASN enrichment | universal |
| **AAAA** (28) | IPv6 address | IPv6 readiness | plain IP | **15/25 [s]** |
| **CNAME** (5) | alias to another name | "why is this going to the CDN" | the target; good tools show the **whole chain** | universal on `www` |
| **MX** (15) | mail exchanger | mail routing, migrations | `pref host`, sorted by pref | **25/25 [s]** |
| **NS** (2) | delegation | "who runs this zone" | name list; better tools name the **provider** | universal |
| **SOA** (6) | zone apex params | serial drift, negative-cache TTL | best tools decode all 7 fields to durations & de-obfuscate the RNAME (`dns.cloudflare.com` -> `dns@cloudflare.com`) | universal |
| **TXT** (16) | free text | everything else (see Tier 5) | quoted strings; only NsLookup.io labels them semantically | universal |

### Tier 4 — long tail (offer, decode lazily)

`NAPTR`(35) ENUM/SIP rewrite rules, still used in telco · `DNAME`(39) subtree alias · `URI`(256) a URL in DNS, genuinely nice to render as a link · `OPENPGPKEY`(61) & `SMIMEA`(53) key/cert publication, both huge base64 blobs · `LOC`(29) lat/long/alt, renders beautifully on a map & is the single most "fun" type · `CERT`(37) · `HINFO`(13) · `RP`(17) · `KX`(36) · `AFSDB`(18) · `IPSECKEY`(45) · `APL`(42) prefix lists · `EUI48`(108)/`EUI64`(109) MACs · `HIP`(55) · `DHCID`(49) · `TA`(32768). All verified live on `*.dns.netmeister.org`, which is the best test corpus available & is worth hardcoding into our own test fixtures.

**Two types missing from the prior pass, found by diffing `miekg/dns`'s `TypeToRR` against this tier:** `AMTRELAY`(260, RFC 8777) multicast tunneling relay gateway list — **observed live** at `amtrelay.dns.netmeister.org` (`\# 18 0A022602F977...`, `TYPE260`; too niche to prioritize decoding but cheap to list) · `RESINFO`(261, RFC 9606, IANA-registered 2023-11-02) resolver capability/policy key-value record (same wire shape as TXT, keys incl. qnamemin support, EDE support) — **registered & implemented in `miekg/dns`, but not confirmed live anywhere by me**; `resinfo.dns.netmeister.org` resolves an A record, not an actual RESINFO answer, so don't take that hostname as a live example. It's the type DigWebInterface's own comparison row above already names as a gap (it skips RESINFO) without ever explaining what it is — now defined.

**Skip or hide:** `SPF`(99) — the dedicated type was dropped by RFC 7208 ("RRTYPE 99 has not seen any substantial use"), SPF lives in TXT; confirmed live, `netmeister.org` returns NODATA for TYPE99 while its TXT carries `v=spf1 a -all`. `AXFR`/`IXFR`/`TKEY`/`TSIG`/`OPT`/`ANY` are transfer/meta types, not lookups. `MD MF NSAP NSAP-PTR NXT A6 MAILA DLV` are dead. `HHIT`/`BRID`(67/68, RFC 9886, Dec 2025), `WALLET`(262), `CLA`/`IPN`(263/264, draft), `UNECE`/`ISO`(69/70, registered 2026-08-20 off a draft) are too new to have deployment.

### Tier 5 — TXT-carried conventions (the highest-value work)

Not types. Parsing & judging these is where a dig-wrapper stops being a dig-wrapper, and it needs **zero third-party data feed**.

| Convention | Owner name | Firsthand sample | Why it matters |
|---|---|---|---|
| **SPF** | apex TXT | `netmeister.org` -> `"v=spf1 a -all"` | 10-lookup limit is the classic silent failure; counting it recursively through `include:` is a pure function |
| **DMARC** | `_dmarc.<d>` | `paypal.com` -> `v=DMARC1; p=reject; rua=…,…; ruf=…` | `p=none` vs `quarantine` vs `reject`, `sp=`, `pct=` are the whole story. **25/25 [s]** publish |
| **DKIM** | `<sel>._domainkey.<d>` | `google._domainkey.netflix.com` -> `v=DKIM1; k=rsa; p=…` | **selector discovery is the hard part** — there is no way to enumerate selectors from DNS. Must guess a wordlist (`google`, `selector1`, `selector2`, `default`, `k1`, `s1`, `dkim`, `mandrill`, `zoho`…). Note `selector1._domainkey.microsoft.com` returns a **CNAME to `…microsoft.onmicrosoft.com` together with `Status: 3` (NXDOMAIN)** — a renderer that only looks at rcode prints "not found" while an answer record was right there |
| **BIMI** | `default._bimi.<d>` | `cnn.com` -> `v=BIMI1; l=…CNN.svg; a=…CNN.pem` | `l=` SVG + `a=` VMC cert; both are fetchable HTTPS URLs worth rendering as a preview |
| **MTA-STS** | `_mta-sts.<d>` | `google.com` -> `v=STSv1; id=20210803T010101;` | The TXT is only a **version+id pointer**; the policy is an HTTPS fetch. Confirmed live: `https://mta-sts.google.com/.well-known/mta-sts.txt` -> `mode: enforce`, 3 `mx:` lines, `max_age: 86400`. Two-protocol check, and MXToolbox already sells it as 8 named sub-checks |
| **TLS-RPT** | `_smtp._tls.<d>` | `google.com` -> `v=TLSRPTv1;rua=mailto:sts-reports@google.com` | one-line parse |
| **Verification tokens** | apex TXT | ~15 distinct vendor prefixes on `github.com` alone | A prefix -> vendor lookup table turns a wall of noise into "Atlassian · Apple · AWS SES · Adobe · Tailscale". Pure data, no API |

## Hard constraints & failure modes

- **Neither free DoH JSON upstream covers the long tail, and they do not fail the same way.** Verified side-by-side 2026-09-16 against `*.dns.netmeister.org`: both return RFC 3597 hex for `LOC URI APL CSYNC EUI48 SMIMEA HIP`; **Cloudflare decodes `ZONEMD` and `OPENPGPKEY` where Google returns hex**; both decode `IPSECKEY NAPTR SSHFP TLSA CAA HTTPS SVCB DNSKEY DS NSEC3PARAM DNAME`. Separately, **Google rejects unfamiliar type *names* with HTTP 400** (`OPENPGPKEY ZONEMD LOC URI APL CSYNC EUI48 SMIMEA` all 400); passing the numeric code gets HTTP 200 and hex. **Cloudflare accepts every one of those mnemonics** (HTTP 200). **Option A caps the tool at roughly the union of the two decoders, ~25 types, and forces a name->number table for Google.**
- **The two upstreams disagree on formatting of the same RRset.** Hex: Google lowercase & unspaced, Cloudflare uppercase & space-separated, often wrapped in `( )`. NAPTR strings: Google strips the quotes, Cloudflare keeps them. RRset **order differs** (Google returned `issuewild` first for `cloudflare.com` CAA, Cloudflare returned `iodef`; the two returned different first records for `cert.dns.netmeister.org`). Cloudflare also returns the **root zone's `Question.name` as `""`**, Google as `"."`. Never depend on order; sort before diffing.
- **Old resolvers fail open, not loud.** `DiG 9.10.6` given `cloudflare.com HTTPS` silently issues two type-A queries; same for `ZONEMD`, `SVCB`, any newer mnemonic. Any shell-out-to-dig design inherits the host's dig version as a correctness dependency. Argues for B.
- **Unknown type numbers must render as `TYPE<n>`, not be dropped or renamed.** NSEC/NSEC3 bitmaps carry `TYPE128`/NXNAME today and something else next year. Google's own front end gets this wrong: `dns.google/query`'s `rrTypeToString` has 45 cases and prints `UNKNOWN_<n>` for everything else, incl. SVCB.
- **NODATA vs NXDOMAIN must be distinguishable.** `Status: 0` + empty `Answer` = the name exists but has no record of that type; `Status: 3` = the name does not exist. Rendering both as "no records" is the most common bug in this category, and `selector1._domainkey.microsoft.com` shows the nastier variant: `Status: 3` **with** a CNAME in the answer section. The SOA in the authority section is where the negative-cache TTL comes from.
- **Underscore-prefixed types return NODATA at the apex,** which reads as "broken" to a user. Tier 2/4/5 needs the prefix helper (option G) or it will generate support questions.
- **DKIM selectors cannot be enumerated.** Any "DKIM check" is a guess against a wordlist & must say so.
- **DNSSEC types are invisible without the DO bit.** Forgetting `+dnssec` makes a signed zone look unsigned.
- **`ANY` is not a feature, and it fails two different ways.** `cloudflare.com`'s authoritative returns the RFC 8482 synthesized `HINFO "RFC8482"` (observed via `dns.google`), while the `1.1.1.1` resolver refuses ANY outright: `Status: 4` (NOTIMP) + `EDE(21) Not Supported` (observed; RFC 8482 does **not** sanction that rcode, it is Cloudflare's own behaviour). Offering `ANY` as "show me everything" teaches users something false. Fan out N typed queries instead.
- **Rate limits are undocumented for the two DoH upstreams, but not for every third party.** Google's DoH JSON page documents **no** rate limit and **no** API key, same for Cloudflare's. `nslookup.io` is the counterexample: it doesn't publish a number in docs, but its live response headers do — `x-ratelimit-limit: 30` per 60s on `/api/v1/records`, `x-ratelimit-limit-autocomplete: 50` — so "undocumented" isn't the same as "unmeasurable"; check headers before assuming. Assume unannounced throttling elsewhere and keep our own fan-out small, which a lazy long-tail dropdown (option D) does anyway.
