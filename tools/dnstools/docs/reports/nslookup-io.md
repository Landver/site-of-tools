# NsLookup.io

The best-designed consumer DNS lookup on the web, and the closest thing to a direct competitor for what we'd build. Run by **Ruurtjan Pul** (Founder/Editor, ex-BigData Republic) w/ **Jeff Westhead** (technical writer, 28 yrs network engineering, ex-Microsoft DNS in Windows & Azure) as a small bootstrapped team. Matters to us for 3 reasons: it proves a **path-shaped permalink** (`/domains/<d>/dns-records/`) is enough UI for the whole product, it ships a **free, keyless, documented REST API** whose response shape is worth copying verbatim, and its whole business is *free lookup -> free monitoring signup*, so the lookup itself is engineered as a funnel, not a product.

- **URL:** https://www.nslookup.io/ · **Category:** DNS lookup + zone health + email/cert security suite · **Registration:** none for any lookup; account only for monitoring · **Pricing:** lookups free; **all six** monitoring products priced **$0/mo, no credit card** (checked 2026-09-16) · **API:** free, **no auth**, OpenAPI 3.1 at `docs.nslookup.io/openapi.yaml`, IP rate-limited
- **Firsthand check (2026-09-16):** curl'd `/robots.txt`, `/sitemap.xml` (129 URLs), downloaded & grepped **all 54 JS bundles** (`main-*` + 53 lazy chunks), called `/api/v1/records`, `/api/v1/records/other`, `/api/v1/propagation`, `/api/v1/dns-health/{d}` (3 zones), `/api/v1/dns-change-review`, the OG-image endpoint, JSON-RPC'd `mcp.nslookup.io/mcp` (`initialize` + `tools/list`), pulled npm + GitHub `LICENSE`, cross-checked answers w/ local `dig`. Result pages are client-rendered: my curl of `/domains/corpberry.com/dns-records/` returned a **22,615-byte** Angular shell titled `Nslookup.io` w/ no record data in it, so rendered-UI claims below are sourced to the bundle where a string was findable and to the companion [firsthand UI observations](./firsthand-ui-observations.md) otherwise, marked as such.

## What it is

Started as a single clean "what are this domain's DNS records" page and accreted a suite: zone health scoring, pre-deploy change review, cert/BIMI checks, security & AI-readiness scanning, an MCP server, and six free monitoring products. Positioning line on `/about/` is "Simplicity perfected". The **education layer is staffed, not incidental** — a dedicated technical writer and **48 `/learning/` articles** plus an index (49 `/learning/` URLs in the sitemap), incl. the deliberately contrarian *"DNS propagation does not exist"*. That's the retention mechanic: the lookup gets you in, the explainers keep you.

## Registration, access & pricing

Everything in the Features table below runs anonymously. No account, no key, no captcha wall for API callers. Sign-in gates only the **monitoring portal** and the 6 `my_*` MCP tools. Every monitoring product page carries the same panel, **"Free / $0 per month / All features included, no credit card required"**: DNS monitoring, SSL monitoring, uptime monitoring ("completely free forever", 1-minute intervals), VMC monitoring, Website Insights, and status pages (unlimited pages, unlimited email subscribers) — all checked 2026-09-16. Historically parts of this were paid, so treat $0 as a growth-phase price, not a permanent one.

## Record types & query options supported

**52 RR types.** Marketing says 53 (MCP `serverInfo`, the `dns_record` tool blurb and the `/records/other` spec description all repeat it), but **three independent machine-readable enums all contain 52**: the MCP `dns_record` inputSchema, the OpenAPI `propagation` enum, and the live 422 validation message from `/api/v1/records/other`. The list: A AAAA AFSDB APL AXFR CAA CDNSKEY CDS CERT CNAME CSYNC DHCID DLV DNAME DNSKEY DS EUI48 EUI64 HINFO HIP HTTPS IPSECKEY IXFR KEY KX LOC MX NAPTR NS NSEC NSEC3 NSEC3PARAM NXT OPENPGPKEY OPT PTR RP RRSIG SIG SMIMEA SOA SPF SRV SSHFP SVCB TA TKEY TLSA TSIG TXT URI ZONEMD. Modern types (HTTPS, SVCB, ZONEMD, CSYNC) are in the API; **HTTPS and SVCB are reachable only via the API or their per-type landing page, not the records-page dropdown**. AXFR/IXFR/TKEY/TSIG are listed but are transfer/meta types you cannot usefully ask a public resolver for.

**Knobs:** choose resolver · `authoritative` mode that discovers the zone's NS and queries one directly · **Show raw data** toggle (`showRawOutput` binding in the bundle) · human-readable vs decoded rendering. **Absent:** no trace/delegation walk, no TCP toggle, no EDNS Client-Subnet, no explicit DO/DNSSEC-OK flag, no NSID, no custom resolver IP. DNSSEC appears only as *audit verdicts* in the health report and as raw DNSKEY/DS/RRSIG/NSEC types, never as a validation chain view.

Resolver picker is richer in the UI than in the documented enum: tabs **Cloudflare | Google DNS | Authoritative**, a **Control D** dropdown by filtering policy (`controldunfiltered`, `controldmalware`, `controldadstracking`, `controldsocial`, `controldfamilyfriendly`) and a **Local DNS** dropdown grouped by continent. Documented API enum has 15 entries, adds `cloudflare2`, and omits the Control D entries.

## How it works

**Entirely server-side.** Angular SPA (`main-*.js` + 53 lazy route chunks) talking to a **NestJS** backend behind Cloudflare (`x-powered-by: Express`; 404s and 422s are NestJS-shaped `{statusCode, timestamp, path, method, error, message}`). Three backends by prefix: `/api` (DNS), `/scanner-api` (security scan), `/portal-api` (certs, VMC, uptime, GEO). Browser never does DNS; it can't.

Methods are inconsistent and worth knowing before you diff against them: `/api/v1/records` **GET**, `/api/v1/records/other` **GET** (the param is `type`, *not* `recordType`), `/api/v1/dns-health/{domain}` **GET**, but `/api/v1/records/webservers` and `/api/v1/propagation` are **POST** (and propagation's param *is* `recordType`). Envelopes differ too: `/records` returns `records.{a,aaaa,ns,mx,txt,cname,soa}`, `/records/other` returns a single `queryResult`.

Queries are **recursive by default** against public resolvers, w/ an opt-in authoritative mode. Every answer carries its provenance: `query.server = {ip, domain, location{lat,lon}, isRecursive}`, plus `rCode` and the header flag set (`queryResponse`, `authoritativeAnswer`, `truncated`, `recursionAvailable`, `authenticatedData`, `securityCheckingDisabled`; no `recursionDesired`). Answers are enriched per record w/ `cnameChain` and, for address records, `ipInfo {country, regionName, city, lat, lon, org, as, asname}` — the same geo/ASN join our `iptools` already does.

TTL handling is the nice part: for an **empty** answer the response still carries the zone's SOA in `authority[]`, **already field-decoded** (`host, admin, serial, refresh, retry, expire, minimum`) rather than raw-only. Confirmed firsthand: my MX and CNAME lookups for `corpberry.com` both returned `answer: []` w/ one decoded SOA in `authority[]`. That is where the UI's negative-cache TTL and honest "No CNAME record found" rows come from. Nothing is cached on their side that I could observe: `cf-cache-status: DYNAMIC` on API calls, each request re-queries.

Three firsthand caveats. (1) The `location` attached to an anycast resolver is **registry geolocation, not the PoP that answered**: they report `1.1.1.1` at −27.4816/153.0175 (Brisbane) while my own `dig @1.1.1.1 ch txt id.server` returned `txl01` (Berlin). I did not establish which geo source they use. (2) The same problem hits *answer* IPs: Cloudflare anycast `188.114.97.0` came back tagged `Medellín, Colombia`. Any geo we print off an anycast address is decoration, not fact. (3) In `server=authoritative` mode they correctly name the server they used (`dion.ns.cloudflare.com`, `isRecursive: false`) but report **`authoritativeAnswer: false` *and* `recursionAvailable: true`** — two flags that an authoritative-only NS cannot both emit; my `dig +norecurse` against that same NS returned `flags: qr aa` w/ no `ra`. Whatever header block they surface, it is not the header of the authoritative query. Do not trust their flags.

## Output & UX

The result URL **is** the query: `/domains/<domain>/dns-records/`, `/domains/<d>/dns-health/`, `/domains/<d>/dns-propagation/<type>/`, `/ip/<ip>/domain-names/` (all verified live; the site 301s to the trailing-slash form). No POST, no form resubmit, shareable and crawlable — and `robots.txt` disallows only `/autocomplete/` and `/*?*`, i.e. path permalinks are indexable by design while anything query-shaped is not.

Rendered page (companion browser session, except where noted): an **"Overall result" header naming the DNS provider**, then A / AAAA / CNAME / TXT / NS / MX cards, then "Other records" w/ the type dropdown. The strings `Overall result`, `Additional record type`, `Start of authority` and `Want to monitor` are all present in the shipped bundle, as are per-type components `app-txt-records`, `app-mx-records`, `app-ns-records`, `app-soa-records`, `app-spf-records`, `app-raw-records` and a duration formatter `app-duration`. TTL is reported as **"Revalidate in 5m"** w/ a sentence about re-asking an authoritative NS; that exact wording is browser-observed only, and the string does not appear anywhere in the 54 chunks I downloaded, so it is composed at runtime or I missed its chunk. TXT records are **semantically labelled** ("Site ownership verification · Google"); the API returns only `raw` + `strings`, so the classification must be frontend-side, but **I could not find the lookup table**: the only `google-site-verification` occurrence in all 54 chunks sits inside the bundled Datadog RUM SDK's meta-name allowlist, unrelated to TXT. SOA is presented field by field: the numeric decode comes from the API, the human durations (`2h 46m 40s`) and the `dns.cloudflare.com` -> `dns@cloudflare.com` de-obfuscation are frontend. Empty results are first-class rows ("No mail servers found"), not blank sections. Loading is per-section: the common 7 render from the first response, the long tail fires a second request only when picked. A `Domain Health` panel and a "Want to monitor this domain?" CTA sit inline. Health reports get a generated OG image (verified: 1200×630 PNG, 13,409 bytes, `cache-control: public, max-age=3600`) so a shared link previews as a score card. No CSV/JSON export button; the API is the export.

## Monetization, limits & abuse controls

Lookups are free and unmonetized directly. Four revenue/funnel paths: (1) **monitoring signup** as the in-product CTA, currently $0 across all six products — land-grab pricing; (2) **SEO volume** — 129 sitemap URLs, 52 per-type landing pages, 48 learning articles; (3) GTM (`GTM-W5FTLHDF`) + a Brevo popup SDK + Datadog RUM (`sessionSampleRate: 10`, `sessionReplaySampleRate: 10`), all confirmed in the bundle; (4) **affiliate referral**, and it is bigger than a footer column: **the entire "Email & Security" nav group is outsourced to easydmarc.com** w/ `utm_source=nslookup` on the headline entries (DKIM/DMARC/SPF checkers, DKIM/DMARC/SPF generators, DMARC report analyzer, DNS record checker, Domain Scanner, IP reputation, phishing-URL, BIMI lookup). A second placement sits in the footer: **"DNS lookup API" -> whoisfreaks.com**. They sold the whole email-tooling category rather than build it.

Documented rate limits, per IP: DNS lookup/propagation/health **30 req/min**; SSL, BIMI/VMC, uptime, GEO **100 req/min**; security scan **5/min and 20/hour**. Observed live on `/api/v1/records`: `x-ratelimit-limit: 30`, `x-ratelimit-remaining: 29`, `x-ratelimit-reset: 60`, plus a separate `x-ratelimit-limit-autocomplete: 50` bucket. I did not push to an actual 429. Cloudflare in front of everything. The **website** additionally mints a **reCAPTCHA v3** token per lookup (site key `6LdjpMwsAAAAAMK84-rKp6djc7l3jln_27MvSuuP`, in the bundle) — but the public API accepted my curl w/ no token and no key, so reCAPTCHA protects the browser path only. **No CORS on `/api/v1/*`** (no `access-control-allow-origin` returned w/ an `Origin: https://example.com` header), so no one can build a browser-only frontend on their API; `mcp.nslookup.io` by contrast sends `access-control-allow-origin: *`.

## Ideas worth stealing

- **Path permalink + trailing-slash normalization.** `/domains/<d>/dns-records/`: domain in the path, crawlable, shareable, cacheable. For us: a `GET`-shaped form -> `ip.corpberry.com/domains/{domain}/dns-records`, Echo route param, htmx `hx-get` + `hx-push-url` for the resolver switch. Costs nothing and kills the "paste the result" problem. (The report previously claimed their component subscribes to `hashchange` to re-run on resolver change; the only `hashchange` listeners I found are in Angular's own `PlatformLocation`, so treat the hash mechanism as unconfirmed.)
- **Ship the SOA on empty answers.** Verified: their empty CNAME/MX responses carry the zone SOA in `authority[]`, decoded into `{host, admin, serial, refresh, retry, expire, minimum}`. That is what lets them print both "No mail servers found" *and* a negative-cache TTL (RFC 2308: min of SOA MINIMUM and the SOA RR's own TTL). One `dig` already returns this; most tools throw it away. Free depth.
- **The finding struct.** Verified verbatim off a live `dns-change-review` call: `{id, title, severity, kind, category, evidence[], recommendation, affectedRecords[]}` — `severity` (how urgent) and `kind` (breaking / best-practice / informational) are **orthogonal**, and `evidence` is an array of plain sentences quoting the actual data ("Current apex NS: dion.ns.cloudflare.com, lisa.ns.cloudflare.com."). Copy this struct wholesale for any Go rule engine; it makes a check self-explaining without a docs page per rule.
- **Tri-state check results.** Their health checks use `pass: true | false | null`, where `null` means not-applicable (every MX sub-check on a zone with no MX). A Go `*bool` or a three-valued enum, and the UI stops printing green ticks for things it never evaluated.
- **Pre-deploy change review — the genuinely novel mechanic.** Load the live zone, let the user edit the proposed state, compare deterministically. The endpoint is `POST /api/v1/dns-change-review` w/ `{domain, proposed}` where `proposed` is BIND zone-file text (the MCP schema also accepts a structured array); it is **undocumented, absent from their OpenAPI spec**, and I found the param name by probing. It returns `{domain, riskScore, riskLevel, summary{critical,high,warning,info}, currentRecords[], proposedRecords[], diff{added,removed}, findings[], warnings[]}` — note it echoes the parsed current *and* proposed state plus an explicit diff, which is most of the UI for free. My probe (replace the apex A, drop everything else) returned `riskScore: 80 / "critical"` w/ `ns_removed`, `dmarc_missing`, `www_removed`, `propagation_risk_high_ttl`. Rules worth having: SPF lookups counted recursively through includes against the 10-lookup limit; DMARC weakened `reject -> none`; all MX removed; apex CNAME and CNAME-conflict; MX target that is itself a CNAME; NS delegation removed/reduced; DS removed; proposed CAA vs the issuer actually serving the site; apex/`www` disappearing; CDN CNAME -> direct origin; high TTL on a record being changed. This is a pure-function domain package: input current + proposed, output findings. Exactly rule #1 in our CLAUDE.md, and it's the one feature in this category nobody else ships.
- **Many resolvers, one prober.** Their propagation check runs from a single vantage point (`queryLocation: "SanFransisco"` on all 32 results) against a hardcoded table of 30 resolver IPs w/ lat/lon and continent. No distributed infrastructure, no Globalping dependency, and it still renders as a world map. That is the affordable version of propagation checking and it is entirely within reach of one Go binary.
- **Attribute the provider above the data.** "Overall result: Cloudflare" derived from the NS suffix, before any record renders. Answers the question most people actually came with. An NS-suffix -> provider map is a small static table.
- **TTL as a duration + a sentence.** "Revalidate in 5m" beats `300`, and one line explaining what happens at expiry converts a lookup into a lesson. Same for SOA: label every numeric field and print `2h 46m 40s`.
- **Semantic TXT labels.** Prefix-match TXT strings (`google-site-verification=`, `v=spf1`, `v=DMARC1`, `v=BIMI1`, `MS=`, `_domainkey`) to a short human label. Pure string table, no dependency, and it's the single thing that makes their TXT card look smarter than everyone else's.
- **OG image per result.** A generated PNG score card for a shared health-report link. In Go this is `image/draw` + a font, cached an hour. Cheap virality for a portfolio tool.
- **Rate-limit headers as a feature.** `x-ratelimit-limit/remaining/reset` on every response, w/ named buckets (they run a second `-autocomplete` bucket alongside the main one). Trivial middleware, makes an unauthenticated API feel professional.
- **Lazy long-tail types.** Render the common 7 from one query; make the other 39 a searchable dropdown that fires a second request. Straight htmx `hx-get` on `<select>` change.
- **Serve MCP over the same domain layer.** Their MCP server is a thin wrapper over the same REST API (Apache-2.0, 4 deps). If our domain package returns structs and handlers do content negotiation, an MCP surface is nearly free — and it is genuinely differentiating for a personal tools site in 2026.

## Gaps & what it does not do

No **delegation trace** / root-down walk (intoDNS and DigWebInterface both do). No **DNSSEC chain visualization** (DNSViz's whole product) — DNSSEC is audit booleans only. No EDNS Client-Subnet, no TCP/UDP toggle, no NSID, no custom resolver IP, no per-resolver latency figures on the records page. No zone-transfer/subdomain enumeration or passive-DNS/recon angle (DNSDumpster's audience). No historical record archive on the free side — history is a monitoring feature. No CSV/JSON download button in the UI. No CORS, so nobody can build on the API from a browser. The whole email-tooling category is an affiliate handoff rather than a product. And the health heuristics show the usual false-positive risk: for a zone with **no DNSSEC at all**, `validation_status` and `ds_dnskey_match` both returned `pass: true` — vacuously true, and misleading next to four red DNSSEC rows on the same card.

I opened neither extension listing beyond confirming they resolve (Chrome 301s to `chromewebstore.google.com`, Firefox 200), so I have no install counts or permission manifests.

## Open source / reusable

Only the MCP layer is open: **[NsLookup-io/nslookup-mcp](https://github.com/NsLookup-io/nslookup-mcp)**, **Apache-2.0** (verified by reading the repo's `LICENSE`), published as `@nslookup-io/mcp-server` (v1.6.1, 16 versions, deps `@modelcontextprotocol/sdk`, `express`, `jose`, `zod`). The hosted server reports 1.6.0, one patch behind npm. It is a thin client over the public REST API, so it is the best-documented map of that API's behaviour and worth reading before writing our own tool schemas. The **OpenAPI 3.1 document is public** and usable as a spec skeleton, though it is stale in places (it advertises "11 tools" where the live server has 23, and omits `dns-change-review` entirely). Because the whole API is free and keyless, it is a legitimate reference implementation to diff our own output against while building, subject to their 30 req/min.
